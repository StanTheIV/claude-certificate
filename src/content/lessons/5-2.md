# Design Effective Escalation and Ambiguity Resolution Patterns

## What actually triggers escalation

An agent that never escalates is dangerous; an agent that escalates everything is useless. The exam treats escalation as a calibration skill with clear, specific triggers:

1. **The customer explicitly asks for a human** ("let me talk to a manager"). Escalate immediately.
2. **A policy gap or exception.** The customer's request is real, but your policy doesn't address it — not because the case is "complex," but because there is genuinely no rule to apply.
3. **Inability to make meaningful progress.** After a reasonable number of attempts, the agent is not converging on a resolution.

Notice what is *not* on this list: case complexity by itself, or a topic that merely sounds hard. A complex-sounding case with a clear applicable policy should still be resolved autonomously. The trigger is the specific situation (explicit request, gap, stuck), not a vague sense of difficulty.

> **Key idea:** Escalation criteria should be specific enough to write down as rules, not left to a general sense of "this seems hard." Write them into the system prompt with few-shot examples showing escalate-vs-resolve decisions.

## Why sentiment and self-reported confidence are unreliable

Two tempting shortcuts for deciding when to escalate both fail, for different reasons:

**Sentiment analysis** ("customer sounds angry, so escalate") confuses *mood* with *case complexity*. A furious customer can have a simple, policy-covered request (a clearly eligible refund). A calm customer can have a genuinely ambiguous edge case. Sentiment does not correlate reliably with whether the agent can actually resolve the issue.

**Self-reported model confidence** ("rate your confidence 1-10, escalate below a threshold") fails because the model's confidence and its actual correctness are not well correlated on hard cases. A model can be confidently wrong precisely on the cases it most needs to escalate — self-reported confidence is a poor proxy for calibrated accuracy.

> **Exam trap:** Both of these sound like reasonable, low-effort signals, and both show up as distractors. The deciding principle: escalation triggers must be tied to observable facts about the *request* (an explicit ask, a policy gap, stalled progress), not to a mood reading or the model's own self-assessment.

## Acknowledge, offer, escalate only on reiteration

Not every expression of frustration is a request for a human. The correct pattern is nuanced:

```
Customer: "This is outrageous, I'm very unhappy with the quality!"
Agent: [acknowledges frustration] "I understand your frustration."
       [offers resolution] "I can offer a replacement or a refund."
Customer: "No, I want to talk to someone!"
Agent: [customer insists again -> immediate escalation]
```

Acknowledge the emotion, then propose a concrete resolution the agent is actually capable of delivering. Only escalate if the customer reiterates the desire for a human after that offer. Escalating on the *first* sign of frustration wastes the resolution the agent could have provided; refusing to escalate after the customer repeats the request ignores an explicit signal.

Compare this to a genuinely explicit request from the start:

```
Customer: "I want to speak to a manager"
Agent: [immediately calls escalate_to_human]
NOT: "I can help with your issue, let me..."
```

When the request is explicit from the first message, do not attempt investigation or an offer first — honor it immediately.

## Escalating for a policy gap, not just a hard case

A policy gap is different from a hard case: the request is often simple to understand, but the policy is silent on it.

```
Customer: "Competitor X has this item 30% cheaper — give me a discount"
Policy: covers price adjustments only on your own site
Agent: [escalates — policy does not cover competitor price matching]
```

The agent should not improvise a discount (that invents policy it doesn't have authority for) and should not simply refuse (the request might be legitimate and a human may have discretion). Escalating hands the decision to someone with the authority to make an exception or explain the boundary.

## Multiple matches: ask, don't guess

When a lookup tool returns more than one matching customer or order, the agent must **ask for additional identifiers** — full name plus email, or an order number — rather than picking one match based on a heuristic (most recent order, first result, closest name match). A wrong guess here risks acting on the wrong customer's account, which is a much worse outcome than asking one clarifying question.

On escalation, hand the human a **structured, self-contained summary**, since the human reviewer typically does not see the full transcript:

```json
{
  "customer_id": "CUST-12345",
  "issue_summary": "Refund request for a damaged item",
  "order_id": "ORD-67890",
  "actions_taken": [
    "Verified customer via get_customer",
    "Confirmed order via lookup_order",
    "Offered a standard replacement — customer insists on a refund"
  ],
  "recommended_action": "Approve a full refund",
  "escalation_reason": "Customer requested to speak with a manager"
}
```

## Exam lens: why the distractors lose

- **Sentiment-based escalation vs. explicit-trigger escalation** — mood doesn't predict case complexity; the deciding principle is that triggers must be observable facts about the request, not an emotional reading.
- **Self-reported confidence threshold vs. explicit criteria with few-shot examples** — a model's own confidence is poorly calibrated exactly where it matters most (hard cases); explicit written criteria don't depend on the model judging itself.
- **A trained classifier that predicts escalation vs. prompt-level escalation criteria** — building a classifier is over-engineered as a first step; it requires labeled data and infrastructure when a prompt fix (explicit criteria plus few-shot examples) hasn't been tried yet.
- **Escalating on the first sign of frustration vs. acknowledge-then-offer** — jumping to escalation before offering a capable resolution wastes agent capability; escalate only once the customer reiterates the request for a human.
- **Guessing the right customer from multiple matches vs. asking for an identifier** — a heuristic guess risks acting on the wrong account; one clarifying question is cheap insurance against a costly error.
- **Refusing a competitor price-match request outright vs. escalating for a policy gap** — silence in the policy is not the same as "no," and a flat refusal forecloses a decision that belongs to a human with discretion.
