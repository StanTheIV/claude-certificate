# Design and implement agentic loops for autonomous task execution

## The agentic loop: what makes an agent "agentic"

A plain chatbot answers once and stops. An **agent** repeats a loop: send a request to Claude, look at what it wants to do, act on it, and feed the result back in — until the task is actually finished. This loop is what lets Claude use tools autonomously across many steps instead of just producing one static reply.

The loop, step by step:
1. Send a request to Claude, including the available tools.
2. Receive a response.
3. Inspect `stop_reason` to decide what to do next.
4. If more work is needed, execute the requested tool(s) and go back to step 1 with the result appended.
5. If the model is done, show the final result.

This sounds simple, but the exam cares a lot about step 3: **how exactly do you know the loop should continue vs. stop?** Get that wrong and you either cut the agent off mid-task or spin forever.

> **Key idea:** An agentic loop is not "call the model repeatedly until it seems done." It is a precise state machine driven by one field in the API response: `stop_reason`.

## `stop_reason`: the only reliable signal

Every Claude API response includes a `stop_reason` field. For agentic control flow, two values matter:

| `stop_reason` | Meaning | What your loop does |
|---|---|---|
| `"tool_use"` | Claude wants to call one or more tools before it can finish | Execute the requested tool(s), append results, send another request |
| `"end_turn"` | Claude has nothing more to do — the task (or turn) is complete | Stop looping; return the final response |

The control rule is exactly this: **continue while `stop_reason == "tool_use"`; terminate when `stop_reason == "end_turn"`.** Nothing else in the response is a reliable termination signal. (Other values like `"max_tokens"` and `"stop_sequence"` exist but are not the primary loop-control values tested here — they signal truncation or a hit stop string, not task completion.)

## Feeding tool results back into context

When Claude requests a tool call, your code executes it, then appends the tool's output as a new message in the conversation history (as a `tool_result` block) before sending the next request. This matters because Claude has no memory between API calls — each request is stateless and only "knows" what's in the conversation history you send it.

Concretely, this means:
- Every tool result becomes part of what Claude reasons over on the *next* iteration.
- If you forget to append a result, or truncate it, Claude effectively "forgets" it happened and may repeat the call or hallucinate an outcome.
- The growing history is also why long-running loops need context management (covered in Domain 5) — but the mechanical rule for *this* task statement is simply: tool result in, next request out.

## Model-driven decisions vs. pre-configured decision trees

A key architectural distinction: in an agentic loop, **Claude decides which tool to call next**, based on the current context and prior tool results. This is different from a hard-coded decision tree, where your code inspects the user's input and picks a fixed sequence of steps ("if refund request, call X then Y then Z").

Model-driven control means the agent can adapt: if a lookup returns an unexpected value, Claude can choose a different next tool instead of blindly following a script. This adaptability is *why* teams choose an agentic loop over a scripted pipeline in the first place — the trade-off is that you give up some predictability in exchange for the model handling cases you didn't anticipate.

> **Exam trap:** A question may describe a fixed, pre-programmed sequence of tool calls and ask if this is "an agentic loop." It technically loops, but it is not model-driven — it's a decision tree wearing a loop's clothing. The defining feature of an agentic loop for this exam is that Claude, not your code, chooses the next action based on `stop_reason` and context.

## Anti-patterns to avoid

The exam explicitly tests recognition of these three broken ways to decide when a loop should stop:

1. **Parsing assistant text for completion phrases** (e.g., scanning the response for the string "Task completed" or "Done"). This is fragile — wording varies, and a model can say "I'm done" mid-explanation without actually finishing, or never say it at all while being finished.
2. **Using an arbitrary iteration cap as the primary stopping mechanism** (e.g., `if iterations > 5: stop`). A cap is a reasonable *safety net* against runaway loops, but using it as the primary signal means you might cut off a task that legitimately needs six tool calls, or keep looping needlessly when the model was already done after two.
3. **Checking for the presence of assistant text content** as a completion indicator. Claude can produce explanatory text alongside a `tool_use` block in the same turn — text existing doesn't mean the turn is over.

> **Exam trap:** All three anti-patterns "usually work" in casual testing, which is exactly why they're dangerous — they degrade unpredictably in production. The only signal with a documented, guaranteed contract is `stop_reason`.

## Exam lens: why the distractors lose

- **Text-parsing for completion vs. `stop_reason` check** — text parsing is probabilistic (wording varies); `stop_reason` is a structured, guaranteed field. When a question offers both, the structured field wins.
- **Iteration cap as primary stop vs. `stop_reason` as primary stop** — a cap can be a safety backstop, but never the main mechanism; it stops correct-but-long tasks early and doesn't stop short-but-broken loops at all.
- **"Assistant produced text" as done-signal** — text and tool calls can coexist in one turn; presence of text proves nothing about completion.
- **Pre-configured decision tree presented as "agentic"** — if the next tool is chosen by your code based on input type rather than by Claude based on `stop_reason` and reasoning, it's not the agentic-loop pattern the exam is testing.
- **Deciding principle:** when a question asks "how do you know the loop is done," the deterministic, documented API field (`stop_reason == "end_turn"`) always beats any inference from natural-language content or a fixed counter.
