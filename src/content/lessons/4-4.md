# Validation, Retry, and Feedback Loops for Extraction Quality

## The retry-with-feedback loop

`tool_use` with a schema guarantees syntactically valid output, but semantic errors still slip through: a `total` that doesn't match the sum of line items, a date placed in the wrong field, an amount extracted from the wrong section of the document. After validating the extraction (with Pydantic, JSON Schema business rules, or custom checks), a failed check should trigger a **follow-up request**, not a silent failure or a blind retry.

An effective retry prompt includes three things:
1. The **original document** (so the model can re-examine the source)
2. The **failed extraction** (what it produced last time)
3. The **specific validation error** — not a generic "invalid output," but something like: *"Field 'total' = 150, but sum(line_items) = 145. Re-check the values."*

This gives the model exactly what a human reviewer would need to self-correct: the evidence, the previous mistake, and a precise description of what's wrong. A generic error message ("extraction failed") gives the model nothing to act on differently, so a blind retry tends to reproduce the same mistake.

> **Key idea:** Retry prompts work by giving the model specific, actionable feedback — the document, the wrong answer, and exactly what's wrong with it — not by simply asking again.

## When retry helps — and when it can't

Retry-with-feedback is effective for errors that are fixable by *re-examining the same source*:
- **Format mismatches** — a date in the wrong format, a string where a number was expected
- **Structural errors** — a value extracted into the wrong field
- **Arithmetic inconsistencies** — a stated total that doesn't match the line items, which the model can recompute

Retry is **not** effective when the problem is that the required information simply isn't in the document you gave the model. If a contract's renewal date is only mentioned in a separate amendment document that wasn't included in the request, no amount of "please re-check the total" feedback will produce a correct renewal date — the information isn't there to find. In that case, the fix is to supply the missing document, not to retry against the same incomplete input.

Recognizing this distinction is a key skill: before retrying, ask whether the error is about *how the model read the document* (retryable) or about *what the document contains* (not retryable, needs a different source or a null/unclear result instead).

> **Exam trap:** Retrying repeatedly against a document that never contained the needed field wastes calls and won't converge — the correct move is to accept a null/unclear result (see Lesson 4.3) or fetch the missing source, not to keep re-prompting.

## Tracking detected_pattern for feedback analysis

When a review or extraction tool produces a finding, adding a `detected_pattern` field — describing *which specific code construct or phrase triggered the finding* — turns individual findings into analyzable data:

```json
{
  "issue": "Possible race condition on shared counter",
  "detected_pattern": "unsynchronized increment of a module-level variable inside an async handler",
  "severity": "medium"
}
```

Without this field, you only know that a finding was dismissed by a developer, not *why* it was likely wrong. With `detected_pattern` recorded on every finding, you can aggregate dismissed findings by pattern and see, for example, that "unsynchronized increment" fires ten times a week and is dismissed nine times out of ten — a strong signal that this specific pattern needs a tighter criterion (see Lesson 4.1) rather than the whole category being disabled.

This turns feedback loop design from anecdotal ("developers seem annoyed") into systematic: you can measure false-positive rates *per underlying pattern*, not just per broad category.

## Self-correction: calculated vs. stated values

A model extracting a document that states its own total can be asked to also **compute** that total independently and compare the two:

```json
{
  "stated_total": 150.00,
  "calculated_total": 145.00,
  "conflict_detected": true,
  "line_items": [
    {"name": "Widget A", "price": 75.00},
    {"name": "Widget B", "price": 70.00}
  ]
}
```

Here `stated_total` is what the document says the total is; `calculated_total` is the sum the model computes from the extracted line items; `conflict_detected` is a boolean the model (or your validation code) sets when they disagree. This pattern surfaces a specific class of real-world error — the source document itself is internally inconsistent, or the model misread a line item — without needing an external validation pass. It's a self-correction design built directly into the schema, rather than a downstream check bolted on afterward.

The same idea generalizes: whenever a document contains a value that *should* be derivable from other extracted fields (a total from line items, a duration from start/end dates), extracting both the stated and the derived value and flagging disagreement catches inconsistencies immediately, whether they originate from the source document or from a model extraction error.

## Exam lens: why the distractors lose

- **Retry with a generic "please try again" message** — gives the model no new information to act on; it's likely to reproduce the same error. Specific error feedback (document + failed extraction + exact validation error) is what makes retry effective.
- **Retrying indefinitely when the information is absent from the source** — retries can't invent information that isn't in the document; recognizing this and returning null/unclear (or fetching the missing source) is correct, not another retry.
- **Treating a dismissed finding as noise with no further action** — without a `detected_pattern` field, you can't distinguish "this pattern is broadly unreliable" from "this one instance was unusual"; tracking the pattern enables systematic tightening of criteria.
- **Trusting the document's stated total without recomputation** — a strict schema only guarantees the field is syntactically a number, not that it's correct; extracting a `calculated_total` alongside `stated_total` catches discrepancies a schema alone would miss.
- **Treating every validation failure as the same category of problem** — conflating format/structural errors (retryable) with missing-information errors (not retryable) leads to wasted retries or, conversely, giving up on genuinely fixable errors too early.
- **Building a separate consistency-checking service instead of extracting both values** — over-engineered; asking the model to extract `calculated_total` alongside `stated_total` in the same schema solves the discrepancy-detection problem without new infrastructure.
