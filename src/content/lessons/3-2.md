# Custom Slash Commands and Skills

## Project commands vs user commands

Slash commands are reusable prompt templates you invoke by typing `/name`. Where you put the command file decides who can use it:

- **`.claude/commands/`** (project-scoped) — stored inside the repository, checked into version control. Every teammate who clones or pulls gets the command automatically. Use this for team-wide workflows: `/review` running the team's standard review checklist, `/test-gen` for generating tests in the project's style.
- **`~/.claude/commands/`** (user-scoped) — stored in the developer's home directory, personal, never shared via VCS. Use this for your own shortcuts that shouldn't affect anyone else.

This is the same scoping logic as the CLAUDE.md hierarchy from the previous lesson: project-scoped things reach the team through version control, user-scoped things stay local to one person.

> **Exam trap:** "put the command in `CLAUDE.md`" is not the same feature. `CLAUDE.md` holds always-loaded context and instructions; it is not where you define an invokable `/command`.

## Skills: `.claude/skills/` and `SKILL.md`

Skills are the more capable evolution of slash commands. A skill lives in its own directory with a `SKILL.md` file that carries YAML frontmatter configuration:

```yaml
---
context: fork
allowed-tools: ["Read", "Grep", "Glob"]
argument-hint: "Path to the directory to analyze"
---

Analyze the code structure in the specified directory.
Output a report on dependencies and architectural patterns.
```

`.claude/skills/` is the project-scoped, version-controlled location (same sharing logic as `.claude/commands/`); a personal skill goes in `~/.claude/skills/`. A skill named `review` in `.claude/skills/review/SKILL.md` is invoked the same way as a command: `/review`.

> **Note (current docs):** current Claude Code documentation has merged commands into skills — `.claude/commands/` still works ("legacy, still supported"), but `.claude/skills/` is now the primary format and supports more frontmatter options. The exam guide teaches `.claude/commands/` as the project-command mechanism; treat both as valid, with skills as the richer option.

## `context: fork` — isolating verbose output

Some skills are noisy by nature: a codebase-analysis skill that reads dozens of files, or a brainstorming skill meant to explore many alternatives before settling on one. If that exploration happens directly in the main conversation, it fills up the context window with output the user doesn't need to see step by step.

`context: fork` runs the skill in an isolated sub-agent context instead. The sub-agent does the noisy work — reading files, trying alternatives, reasoning through options — and only its final output flows back into the main session. The main conversation's context stays clean.

Use `context: fork` for:
- Codebase analysis skills that read many files and produce a long report.
- Exploratory or brainstorming skills that consider several alternatives before returning a recommendation.

Skip it for short, deterministic skills where there's nothing to isolate — forking adds sub-agent overhead for no benefit if the skill's own output is already the only output you want.

> **Key idea:** `context: fork` is a context-management tool, not a security tool — it protects the *main conversation's* token budget, not the filesystem. Tool restriction is a separate frontmatter key (next section).

## `allowed-tools` and `argument-hint`

Two more frontmatter keys shape how a skill behaves:

- **`allowed-tools`** restricts which tools the skill may use while it runs. For example, a skill that only writes a changelog file can be limited to `["Write"]`, so it structurally cannot run `Bash` or delete files, even if a crafted input tried to push it that way. This is least-privilege applied to a skill's own execution, not just to the containing agent.
- **`argument-hint`** shows a hint text when a developer invokes the skill without arguments, prompting them for what's required — e.g. `argument-hint: "[ticket-id]"` for a skill that needs a ticket number to run.

```yaml
---
allowed-tools: ["Write"]
argument-hint: "[changelog-entry]"
---
```

Together, these two keys make a skill safer (bounded tool access) and easier to use correctly (a visible hint instead of a silent failure when arguments are missing).

## Skills vs CLAUDE.md, and personal variants

**Skills are on-demand**: they run only when invoked (by name, or when Claude decides the description matches the task). **CLAUDE.md is always-loaded**: every instruction in it is in context from the start of every session, whether or not it's relevant to the current task.

Use this to decide where a piece of guidance belongs:
- A universal standard that should shape *every* response ("always use 2-space indentation") → CLAUDE.md.
- A specific, occasionally-needed workflow ("run our release checklist") → a skill, invoked only when actually releasing.

Putting a rarely-needed workflow in CLAUDE.md wastes context every single session; putting a universal standard in a skill means Claude only follows it when someone remembers to invoke the skill.

**Personal skill variants**: if you want to experiment with a different version of a shared skill without affecting teammates, create it under `~/.claude/skills/` with a different name (e.g. `review-strict` instead of `review`). Your variant is invocable alongside the project's shared `review` skill but stays private to you.

## Exam lens: why the distractors lose

- **Storing a team command in `CLAUDE.md`** loses to `.claude/commands/` or `.claude/skills/` — CLAUDE.md is loaded context, not an invokable command definition.
- **A `.claude/config.json` with a commands array** loses because that file doesn't exist — it's a plausible-sounding invented distractor.
- **`~/.claude/commands/` for a team-wide checklist** loses to `.claude/commands/` — user-scoped commands never reach teammates through version control, so "available to everyone who clones the repo" always means the project-scoped location.
- **Running a verbose analysis skill without `context: fork`** loses to running it *with* `context: fork` — without it, the exploration's full output pollutes the main session's context for the rest of the conversation.
- **Overwriting the shared skill to test a personal tweak** loses to creating a personal variant under a new name in `~/.claude/skills/` — editing the shared file changes behavior for every teammate who pulls it.
- **Putting a rarely-used workflow in CLAUDE.md "so Claude always knows about it"** loses to a skill — it's the wrong mechanism for on-demand guidance and costs context every session for no benefit.
