# Manage session state, resumption, and forking

## Named session resumption: `--resume <session-name>`

A Claude Code (or Agent SDK) session isn't necessarily a single sitting — investigations, refactors, and reviews often span multiple work sessions over hours or days. **`--resume <session-name>`** continues a *specific, named* prior conversation, bringing back its accumulated context (files read, findings, decisions made) instead of starting over.

```bash
claude --resume investigation-auth-bug
```

This is most useful for long-running, named investigations you want to return to deliberately — e.g., you were debugging an auth issue yesterday, want to pick up exactly where you left off today, and don't want to re-explain what you already found.

> **Key idea:** `--resume <session-name>` targets one specific named session, not just "the last conversation." Naming sessions is what makes it possible to juggle several separate investigations and return to the right one.

## `fork_session`: branching from a shared baseline

**`fork_session`** creates an independent branch from an existing session's context — both the original and the fork start from the same shared analysis baseline, then diverge independently from that point on.

```
Codebase investigation
         |
    fork_session
    /           \
Approach A:      Approach B:
Redux            Context API
```

This is the tool for **exploring divergent approaches** without re-doing the shared groundwork twice: you do the initial investigation once (e.g., understand the current state module and its dependents), then fork into two branches to compare two different solutions built on that same foundation — say, comparing a Redux-based refactor against a Context-API-based refactor, or comparing two different testing strategies. Each fork can be explored (and abandoned, or kept) independently.

> **Exam trap:** Re-running the *entire* initial investigation separately for each approach "to keep them independent" wastes the exploration work that was already identical between the two — `fork_session` exists specifically so you don't have to repeat shared groundwork before branching into divergent paths.

## Why stale tool results are dangerous on resume

Resuming a session brings back the full prior context — including the results of tool calls made *then*. If the underlying files or system state have changed since that session (someone else edited the code, a deploy happened, the branch was rebased), those cached tool results are now **stale**: the resumed agent may reason from a Read result or Grep match that no longer reflects reality.

The fix is not to avoid resuming — it's to **explicitly tell the agent what has changed** when you resume: name the specific files that were modified since the last session, so the agent does targeted re-analysis of just those files rather than either (a) blindly trusting stale results, or (b) redoing the entire exploration from scratch.

> **Key idea:** Informing a resumed session about specific file changes enables *targeted* re-analysis — you get the benefit of the preserved context without the risk of the agent reasoning from outdated tool output.

## Resume vs. fresh session with a structured summary

Sometimes the better move isn't to resume at all — it's to **start a new session and inject a structured summary** of the relevant prior findings into the first prompt.

Choose based on how much of the prior session's tool-derived state is still valid:

| Situation | Better choice |
|---|---|
| Prior context is mostly still valid; little has changed | Resume (`--resume <session-name>`) |
| Files/tool results are substantially stale (lots of change since) | Fresh session + structured summary of what was already found |
| A lot of time has passed and context quality has likely degraded | Fresh session + structured summary |
| You want to preserve one thread while trying a different approach | `fork_session` |

The reasoning behind preferring a fresh session with a summary when results are stale: resuming carries forward *all* prior tool outputs, including the now-wrong ones, and the agent has no way to tell which specific pieces are outdated unless told. A fresh session with a concise, accurate summary ("here's what we found last time: X, Y, Z — the codebase has since changed in module A") gives the agent only the information that's still true, without dragging along stale tool results it might mistakenly trust.

> **Exam trap:** "Always resume to preserve maximum context" sounds efficient but is wrong when tool results are stale — more context isn't better if part of it is now false. The deciding factor is whether the *specific* prior tool outputs are still accurate, not how much context there is.

## Exam lens: why the distractors lose

- **Resuming without mentioning file changes vs. resuming and stating what changed** — silently resuming after files changed lets the agent reason from stale Read/Grep results; explicitly naming the changed files enables safe, targeted re-analysis.
- **Full re-exploration from scratch after every file change vs. targeted re-analysis** — re-running the entire investigation over-corrects; naming the specific changed files lets the agent re-check just those.
- **Repeating shared investigation for each approach vs. `fork_session` from one baseline** — redoing identical groundwork for two approaches wastes the exact overlap `fork_session` is designed to avoid.
- **"Always resume to keep maximum context" vs. resume only when context is still valid** — carrying forward stale tool results is a liability, not a benefit; when results are stale, a fresh session with an accurate summary is more reliable than resuming with outdated ones.
- **Deciding principle:** the choice between resume, fork, and fresh-session-with-summary always comes down to whether the previously gathered tool state is still true — preserve it if valid, replace it with a stated summary if stale, and branch it if you need to explore two paths from one valid baseline.
