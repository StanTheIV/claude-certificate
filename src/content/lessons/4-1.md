# Explicit Criteria: Precision and Trust in Review Prompts

## Why vague instructions fail

A prompt like "check that comments are accurate" or "be conservative — only report high-confidence findings" sounds reasonable, but it gives the model no fixed boundary. "Accurate" and "high-confidence" are judged differently on every run, so the same code can be flagged one time and ignored the next. Telling the model to be "more conservative" doesn't fix this: conservative according to what rule? The model has nothing concrete to check against, so it falls back on its own shifting sense of what counts as suspicious.

Compare that to an explicit, categorical instruction: "Flag a comment as problematic only if it describes behavior that contradicts the actual code, references a function or variable that no longer exists, or is a TODO/FIXME for a bug that is already fixed." This is a checklist, not a mood. The model can test each comment against it and get the same answer every time.

This matters most in automated review pipelines (CI comment checks, security scanners) where the same code should never get inconsistent verdicts between runs. Explicit categorical criteria — a closed list of "flag this" and "skip this" conditions — outperform confidence-based filtering because they replace a subjective judgment call with a checkable rule.

> **Key idea:** "Be conservative" is not a criterion — it is a request for the model to guess your threshold. Replace it with a concrete list of what to flag and what to skip.

## Writing criteria that say what to report AND what to skip

A strong prompt defines both sides: which issues are worth reporting, and which are explicitly out of scope. For a code review prompt, that might look like:

```
Report:
1. Bugs that cause incorrect behavior or crashes
2. Security issues (injection, missing auth checks, secrets in code)

Do NOT report:
1. Minor style preferences (naming, formatting) already covered by the linter
2. Patterns that are locally idiomatic in this codebase, even if unusual
3. Missing comments or documentation (a separate review category)
```

Without the "do NOT report" half, the model still has to guess where the line is for borderline cases — style choices that might be bugs, or local idioms that look wrong out of context. Naming the excluded categories explicitly removes that guesswork and keeps the review focused on what the team actually acts on.

This is the same shift as the "flag only if it contradicts code" example: replace confidence language with a rule the model can apply mechanically, the same way on every file.

## False positives erode trust in everything

A review category with a high false-positive rate doesn't just waste time on the wrong findings — it damages how developers treat *every* finding from that tool, including the accurate ones. If a "possible race condition" category is wrong 4 times out of 5, developers learn to skim past all flagged race conditions, including the real one buried in next week's batch. Trust, once lost for a category, doesn't stay contained to that category; reviewers start skimming the whole report faster and missing genuine issues elsewhere.

This is why false-positive rate, not just recall, is a first-class design constraint for review prompts. A category that catches 90% of real issues but is wrong half the time can be net-negative for a team, because the cost is measured in ignored output, not missed bugs alone.

> **Exam trap:** A question may offer "add more categories to catch more issues" as an option when the real problem is that an *existing* category has a high false-positive rate. Adding scope makes a trust problem worse, not better.

## Severity criteria need code examples, not adjectives

"Critical" and "medium" mean different things to different reviewers unless you anchor each level with a concrete example:

```
CRITICAL: Runtime failure affecting users
  Example: NullPointerException while processing a payment

HIGH: Security vulnerability
  Example: SQL injection, XSS, missing authorization check

MEDIUM: Logic bug without immediate user impact
  Example: Wrong sort order, off-by-one error

LOW: Code quality issue
  Example: Duplicated logic, suboptimal algorithm on small data
```

Without the examples, "critical" is just a word the model applies inconsistently — one run might call a style issue "high" because it *sounds* serious. With a worked example per level, the model can compare the current finding's shape to a known anchor case, which produces far more consistent severity labels across files and across runs. This is the same principle as the report/skip lists above: turn a subjective label into something checkable against a concrete reference.

## Restoring trust: temporarily disable noisy categories

When a category is producing too many false positives, the fastest fix for developer trust is not to keep running it while quietly telling reviewers to double-check its output — that just shifts the filtering burden onto humans and defeats the purpose of automation. The better move is to **temporarily disable that category** entirely, so the parts of the review that already work well keep the team's confidence, while you iterate on the noisy category's criteria offline against a sample of known cases.

Once the criteria for that category produce an acceptable false-positive rate on the sample, re-enable it. This keeps the overall tool trustworthy at every point in time, instead of shipping a known-bad category and hoping people notice the pattern themselves.

> **Exam trap:** "Keep the noisy category on but add a disclaimer that some findings may be wrong" looks cheap, but it does nothing to restore trust — developers still have to evaluate every finding manually, which is the exact cost you were trying to remove.

## Exam lens: why the distractors lose

- **"Tell it to be more conservative / only high-confidence" as the fix** — this is still a vague, subjective instruction. It sounds like a tightening of criteria but gives the model no new checkable rule, so results stay inconsistent. Explicit categorical criteria win because they're testable the same way every time.
- **Add a classifier or filtering layer to catch false positives** — over-engineered. It adds infrastructure and a second model call to solve a problem that a clearer prompt (explicit report/skip criteria) already solves for free.
- **Keep a noisy category running with a caveat/disclaimer** — hides the problem instead of fixing it; developers still bear the cost of manually filtering. Temporarily disabling the category is more effective at restoring trust.
- **Add more categories to "catch more issues"** — solves the wrong problem when the actual issue is an existing category's false-positive rate; more scope increases noise instead of reducing it.
- **One-word severity labels without examples** — "critical" and "medium" without anchoring examples stay subjective; concrete code examples per severity level are what make classification repeatable.
- **Blame the model / switch models to fix inconsistency** — inconsistent output from vague criteria is a prompt design problem, not a capability problem; a bigger or different model applied to the same vague instruction will still guess.
