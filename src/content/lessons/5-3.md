# Implement Error Propagation Strategies Across Multi-Agent Systems

## Why generic error statuses fail the coordinator

In a coordinator-subagent system, when a subagent hits a problem, what it reports back determines whether the coordinator can make a good recovery decision. A generic status like `"search unavailable"` tells the coordinator almost nothing: was this a timeout that a retry might fix? A permission problem that won't resolve on retry? Did the subagent find zero real matches, or did it never manage to search at all?

Without that context, the coordinator's only options are to guess or to treat every failure the same way — usually either retrying blindly or giving up. Neither is an intelligent recovery decision; both are shots in the dark.

> **Key idea:** The coordinator can only recover as well as the information it receives. Hiding detail behind a generic status doesn't protect the coordinator from complexity — it just prevents it from responding well to that complexity.

## Access failures vs. valid empty results

A critical distinction that a good error-reporting design must preserve: an **access failure** (a timeout, a connection error, a rate limit) is fundamentally different from a **valid empty result** (the search ran successfully and genuinely found nothing).

If a subagent's search for "AI adoption in dental clinics 2024" times out, and the subagent reports back "no results found," the coordinator will reasonably conclude the topic has no coverage and may write a report that silently omits it. But the truth is the search never actually completed — the topic might have plenty of coverage that was never found. Conflating these two outcomes into one "no results" signal is a silent, costly loss of information.

Reporting must distinguish them explicitly, so the coordinator can decide: retry the query (access failure) versus accept that there's genuinely nothing here and move on (valid empty result).

## Two anti-patterns: suppression and termination

Beyond generic statuses, two more patterns look reasonable but actively make the system less reliable:

| Anti-pattern | Problem |
|---|---|
| Silently suppressing the error (returning an empty result marked as success) | The coordinator believes the query ran cleanly and found nothing, and proceeds as if that's true — hiding a real failure behind a success signal |
| Terminating the entire workflow on a single subagent failure | One subagent's timeout throws away every other subagent's successful, completed work |

Both anti-patterns trade a recoverable situation for an unrecoverable one: suppression hides the fact that recovery was even possible, and termination discards partial progress that didn't need to be discarded at all. The correct middle ground is to surface the failure honestly and let the system continue with whatever succeeded, annotating what didn't.

## Structured error context enables recovery

The fix is to have subagents return a structured error object when they cannot resolve a problem themselves — including the failure type, what was attempted, any partial results already gathered, and possible alternatives:

```json
{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "AI impact on music industry 2024",
  "partial_results": [
    {"title": "AI Music Generation Report", "url": "...", "relevance": 0.8}
  ],
  "alternative_approaches": [
    "Try a narrower query: 'AI music composition tools'",
    "Use an alternative data source"
  ],
  "coverage_impact": "Not covered: AI impact on music production"
}
```

This gives the coordinator everything it needs to decide intelligently: retry with a modified query, use the partial results as-is, delegate to a different subagent or data source, or proceed without this section while explicitly noting the gap. None of those options were available with a bare "search unavailable" string.

Before escalating an error at all, subagents should attempt **local recovery** for transient failures — a small number of retries with backoff, handled inside the subagent — and only propagate to the coordinator the errors they genuinely cannot resolve themselves, along with what was attempted and any partial results. Endless retries inside a subagent waste latency and resources without ever informing the coordinator; local recovery should be bounded, not unlimited.

## Coverage annotations in the final synthesis

When some subagent work was partial or failed, that gap should be visible in the final output, not silently absorbed into a confident-sounding report:

```markdown
## Report: AI Impact on Creative Industries

### Visual Art (FULL COVERAGE)
[research results]

### Music (PARTIAL COVERAGE — search agent timeout)
[partial results]
Note: coverage for this section is limited due to a timeout in the search agent.

### Literature (FULL COVERAGE)
[research results]
```

Structuring synthesis output with explicit coverage annotations — which findings are well-supported and which topic areas have gaps due to unavailable sources — lets the reader calibrate trust in each section, instead of treating the whole report as uniformly reliable.

## Exam lens: why the distractors lose

- **A generic "search unavailable" status vs. structured error context** — hiding the failure type, attempted query, and partial results forces the coordinator to guess; structured context lets it decide.
- **Marking a timed-out search as an empty "success" vs. distinguishing access failure from empty result** — suppression looks harmless but silently corrupts the coordinator's model of what was actually covered.
- **Terminating the whole workflow on one subagent's failure vs. continuing with partial results and annotated gaps** — termination discards every other subagent's completed, valid work over a single localized problem.
- **Unlimited retries inside a subagent vs. bounded local recovery then propagation** — infinite retries burn latency without ever informing the coordinator that something is wrong; a small bounded retry, then propagate with details, balances resilience and visibility.
- **Silently omitting an uncovered topic from the report vs. an explicit coverage annotation** — a clean-looking report that hides its own gaps is more dangerous than one that states them, because the reader can't tell what to double-check.
