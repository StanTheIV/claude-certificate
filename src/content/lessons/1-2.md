# Orchestrate multi-agent systems with coordinator-subagent patterns

## Hub-and-spoke: the default multi-agent topology

When a task is too broad or too varied for one agent to handle well, you split it across specialized **subagents** — a web-search agent, a document-analysis agent, a synthesis agent, and so on. The standard way to wire these together is **hub-and-spoke**: a single **coordinator** agent sits at the hub, and every subagent is a spoke that only talks to the coordinator, never directly to each other.

```
         Coordinator
        /     |      \
   Search   Analysis  Synthesis
```

The coordinator owns:
- **Task decomposition** — breaking the request into subtasks
- **Delegation** — deciding which subagent(s) handle each subtask
- **Result aggregation** — combining subagent outputs into one answer
- **Error handling** — deciding what to do when a subagent fails or times out
- **Information routing** — passing findings from one subagent into the next subagent's prompt

> **Key idea:** All inter-subagent communication flows *through* the coordinator. This isn't just tidiness — it gives you a single place to observe the whole system, apply consistent error handling, and control what information reaches whom.

## Dynamic subagent selection, not a fixed pipeline

A coordinator should analyze what the query actually needs and invoke only the relevant subagents — not always run the full pipeline. A simple factual question might only need the search subagent; a request asking for a fully cited comparative report might need search, analysis, and synthesis. Always running every subagent regardless of need wastes latency and cost, and it isn't what "coordinator" means in this architecture — a coordinator that blindly calls the same fixed sequence every time is functionally just a scripted pipeline with extra steps.

## The risk of overly narrow decomposition

This is a heavily tested failure mode. A coordinator can decompose a broad topic into subtasks that are individually well-executed but collectively too narrow, leaving whole parts of the topic uncovered.

**Worked example:** Topic = "impact of AI on creative industries." The coordinator decomposes it into: "AI in digital art creation," "AI in graphic design," "AI in photography." Every subagent does its job correctly — search finds good articles, analysis summarizes them well, synthesis writes a coherent report. But the final report only covers visual arts; music, writing, and film are missing entirely.

The subagents are not at fault here — they executed exactly what they were assigned. The root cause is upstream, in the coordinator's decomposition step. When diagnosing an incomplete-coverage failure, check what subtasks the coordinator actually generated before blaming any individual subagent's execution.

> **Exam trap:** A question describing this exact pattern (narrow subtopics, each executed well, broad topic under-covered) will offer distractors that blame the synthesis agent ("it should detect gaps") or the search agent ("queries weren't broad enough"). Both blame a spoke for a hub problem. The fix belongs at the coordinator's decomposition step, not downstream.

## Iterative refinement loops

A coordinator shouldn't treat synthesis as a one-shot final step. A stronger pattern: the coordinator evaluates the synthesis output for gaps, and if coverage is insufficient, re-delegates to search and/or analysis subagents with **targeted queries** aimed at the specific gap, then re-invokes synthesis. This repeats until coverage is judged sufficient.

This is different from just re-running the whole pipeline from scratch — the re-delegation is targeted (e.g., "search specifically for AI's impact on music composition and songwriting," not "search again"), because the coordinator already knows exactly what's missing from evaluating the first pass.

## Partitioning scope to avoid duplication

When a coordinator does split work across multiple subagents, it should assign **distinct** subtopics or source types to each one — not have two subagents research overlapping ground. For example: assign one search subagent "academic papers on AI and music" and another "industry news on AI and film production," rather than sending both a vague "research AI in creative industries" that causes redundant, overlapping work and wastes the parallelism you set out to gain.

> **Note:** How subagents are actually invoked (the `Task` tool, `allowedTools`, prompt content) and why they don't share memory is covered in the next lesson (1.3) in detail — this lesson focuses on the coordinator's orchestration responsibilities and decomposition risk.

## Exam lens: why the distractors lose

- **Blaming a downstream subagent for a coordinator decomposition failure** — if subagents individually succeeded but coverage is narrow, the root cause is the subtask list the coordinator generated, not subagent execution quality.
- **Always invoking the full pipeline "to be safe" vs. dynamic selection** — over-invoking every subagent for every query is wasted latency/cost and isn't the dynamic-selection behavior the exam wants; the right call depends on query complexity.
- **One-shot synthesis vs. iterative refinement** — treating synthesis as final without checking for gaps misses the coordinator's responsibility to evaluate and re-delegate with targeted follow-ups.
- **Overlapping subtopic assignment vs. partitioned assignment** — assigning the same broad scope to multiple subagents "for redundancy" wastes parallel capacity that should instead widen coverage.
- **Subagents talking directly to each other vs. routing through the coordinator** — bypassing the hub loses observability and consistent error handling, even if it seems more "efficient" for a single hop.
- **Deciding principle:** when several subagents each did their assigned job correctly but the aggregate output is wrong or incomplete, look one level up — at what the coordinator assigned, not at how well it was executed.
