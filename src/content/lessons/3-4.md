# Plan Mode vs Direct Execution

## What plan mode does

Plan mode is a read-only investigation phase. Claude explores the codebase using tools like Read, Grep, and Glob, builds an understanding of how things currently work, and produces an implementation plan — without making any changes. You review the plan and approve it before Claude switches to actually editing files.

This matters because it separates two risks that are normally tangled together: *understanding the problem* and *committing to a solution*. In direct execution, both happen at once — Claude starts editing based on its first read of the situation, and if that first read was incomplete, the rework happens after code has already changed. In plan mode, the exploration is free of side effects: if the plan turns out to be wrong, you've lost no work, because nothing was written yet.

> **Key idea:** plan mode doesn't make Claude smarter — it moves the point where you can catch a wrong approach from "after several files are already changed" to "before anything is changed."

## When to use plan mode

Plan mode earns its overhead when the task has real uncertainty to resolve before writing code:

- **Large-scale changes** — dozens of files, or a migration touching 45+ files.
- **Multiple valid approaches** — e.g. restructuring a monolith into microservices, where service boundaries could reasonably be drawn several different ways.
- **Architectural decisions** — which framework, which data-access pattern, which module structure.
- **Unfamiliar codebase** — you need to understand the existing structure before you can safely change it.

In each case, the risk isn't "will Claude write correct code" — it's "will Claude change the *right* things, in the *right* order, without missing a dependency it hasn't seen yet." Exploring first, in a mode where nothing can be broken, directly reduces that risk.

## When to use direct execution

Direct execution skips the planning phase and starts implementing immediately. It's the right choice when the change is **simple and well-scoped**:

- A single-file bug fix where the stack trace already tells you exactly what's wrong.
- Adding one validation check to one function.
- Any change where you already know precisely what needs to happen and there's only one reasonable way to do it.

For these tasks, plan mode adds a review step with nothing meaningful to review — the "plan" would just restate the obvious fix. Forcing every trivial change through a planning phase slows the team down without reducing any real risk.

> **Exam trap:** "always use plan mode for safety" sounds cautious but is wrong for well-scoped, single-file fixes — the overhead isn't buying any risk reduction there, just latency.

## The Explore subagent

Some tasks need heavy investigation — reading many files, tracing call chains, searching for every usage of a deprecated function — before any decision can be made, whether or not you formally enter plan mode. Doing all of that directly in the main conversation fills the context window with verbose intermediate output: file contents, grep results, false leads.

The **Explore subagent** is built for this: it runs the verbose discovery phase in an isolated context and returns only a summary to the main conversation. The exploration "scratch work" never enters the main context window.

This is especially valuable in **multi-phase tasks**: a long investigation followed by implementation followed by testing. If the investigation phase alone consumed most of the context window with raw file dumps, there'd be little room left for the implementation and testing phases that follow. Delegating discovery to the Explore subagent keeps that budget available for the rest of the task.

## Combining plan mode with direct execution

The two aren't mutually exclusive — the most effective pattern is often to combine them in sequence:

1. **Plan mode** for investigation and design — explore the codebase, understand the current library's usage, decide on a target structure.
2. You review and approve the plan.
3. **Direct execution** to implement the now-approved plan — the uncertainty has already been resolved, so this phase is just carrying out clear, agreed steps.

Worked example: planning a library migration. Plan mode first explores every call site of the old library, checks for API differences with the replacement, and proposes a migration order. Once you approve that plan, direct execution carries it out file by file — there's no more architectural ambiguity left to resolve mid-implementation.

> **Key idea:** plan mode for "what should we do and why," direct execution for "now do it." Using both together, in that order, avoids paying planning overhead for the *implementation* phase after the decisions are already made.

## Exam lens: why the distractors lose

- **"Start with direct execution and let the structure emerge as you go"** loses to plan mode for architecturally uncertain work — this risks costly rework once dependencies are discovered mid-implementation, exactly what plan mode's upfront exploration avoids.
- **"Write comprehensive upfront instructions detailing the exact structure, then execute directly"** loses to plan mode — it assumes you already know the right structure without having explored the code, which is the assumption plan mode exists to test before you commit.
- **"Begin in direct execution and only switch to plan mode if complexity appears"** loses when the complexity is already evident from the task description — waiting for it to "appear" during implementation means some of it will appear as a half-finished change.
- **Using plan mode for a one-line, clearly-scoped fix** loses to direct execution — added review overhead with no corresponding uncertainty to resolve.
- **Running heavy multi-file discovery directly in the main conversation instead of via the Explore subagent** loses when the task has further phases after discovery — it burns context budget on raw exploration output that a summary would have preserved.
