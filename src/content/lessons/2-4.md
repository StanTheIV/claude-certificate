# Integrating MCP Servers

## What an MCP server gives an agent

The Model Context Protocol (MCP) is how Claude Code and Agent SDK applications connect to external systems without writing a custom integration for each one. An MCP server is a process that exposes **tools** (actions the agent can call, like `create_issue` or `run_query`), and typically also **resources** (data the agent can read for context) over a standard protocol.

Two behaviors matter for how you design around MCP servers:

1. **Discovery happens at connection time.** When an agent connects to an MCP server, all of that server's tools are discovered automatically — you don't manually register each one.
2. **All servers' tools are available simultaneously.** If a project configures three MCP servers (say, GitHub, Jira, and an internal database), the agent sees the union of all their tools at once, alongside its built-in tools. This is exactly why Task Statement 2.1's discipline — clear, differentiated descriptions — matters even more with MCP: the model is choosing not just among your custom tools, but among everything every connected server exposes.

> **Key idea:** Adding an MCP server isn't an isolated integration — it expands the entire tool-selection surface the model reasons over on every turn.

## Project scope vs user scope: .mcp.json and ~/.claude.json

Claude Code supports configuring MCP servers at different scopes, and the exam guide draws the line primarily between two of them:

- **Project scope — `.mcp.json` at the project root.** Checked into version control, so every teammate who clones or pulls the repo gets the same shared servers automatically. Use this for team tooling everyone needs: the GitHub server, the internal issue tracker, a shared database connector.
- **User scope — `~/.claude.json` in the home directory.** Not shared via version control, private to that developer's machine. Use this for personal or experimental servers — something you're trying out, or a connector that's specific to your own workflow, not the team's.

The deciding question when choosing scope is: *should every teammate get this automatically, or is this mine to experiment with?* Shared, standard team tooling goes in `.mcp.json`; personal or in-progress servers stay in `~/.claude.json`.

> **Note (current docs):** Current Claude Code documentation describes three scopes rather than two: **local** (private to you, for the current project, stored under `~/.claude.json`, and the default when you run `claude mcp add`), **project** (`.mcp.json`, shared via version control), and **user** (also in `~/.claude.json`, but available across *all* your projects, not just one). The exam guide's two-way split — project-shared vs. user-personal — is the version to know for the exam; the "local vs. user" distinction (single-project-private vs. all-projects-private) is a newer refinement layered on top of the same project/personal boundary.

## Keeping secrets out of version control: env var expansion

Because `.mcp.json` is committed to version control, it must never contain a literal API token or credential. Instead, the config references an environment variable, and Claude Code expands it at load time:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

`${GITHUB_TOKEN}` is not the token itself — it's a placeholder that gets substituted with the value of the `GITHUB_TOKEN` environment variable already set on the machine running Claude Code. Every teammate keeps their own token in their own environment; the shared `.mcp.json` file never has to change, and no secret ever enters git history. This is the standard pattern for authenticating any shared MCP server (Jira, an internal API, a database) without trading version-control convenience for credential safety.

## Build vs borrow: choosing MCP servers

Before building a custom MCP server, check whether a community one already covers the integration. For standard, well-known systems — GitHub, Jira, Slack — existing community MCP servers already implement the protocol correctly and are maintained by people who track API changes. Reimplementing one from scratch duplicates that effort for no architectural benefit.

Reserve custom MCP servers for genuinely team-specific workflows: an internal deployment system, a proprietary database schema, a bespoke approval pipeline — things no community server could possibly cover because they don't exist outside your organization.

> **Exam trap:** Building a custom server for a standard integration "for more control" sounds thorough, but it's extra engineering and ongoing maintenance burden for a problem the ecosystem already solved. Prefer the community server unless your requirement is genuinely unique to your team.

## Resources: a map before you explore

MCP resources are a different kind of thing from MCP tools. A tool is something the agent *calls* to take an action or run a query; a resource is content the agent can *read directly* to get context — without spending a tool call to "go find out what exists."

Typical resources: a catalog of open issues, a hierarchy of documentation pages, a database schema. Exposing these as resources means the agent doesn't have to make exploratory tool calls just to learn what's available — it can read the catalog once and then make targeted, informed tool calls instead of probing blindly.

This same idea explains a subtler failure mode: if your MCP tool descriptions are thin, an agent may default to a built-in tool like Grep instead of your more capable MCP tool, simply because Grep's behavior is more predictable to it than an under-described custom tool. The fix is the same discipline from Task Statement 2.1 — write MCP tool descriptions that explain concrete advantages and the specific data or context the built-in tool cannot provide, so the agent has a real reason to prefer the MCP tool.

## Exam lens: why the distractors lose

- **Putting a shared team server in `~/.claude.json`** — technically works for you, but it means teammates don't get the server automatically, defeating the purpose of shared tooling. If it should be available to everyone who clones the repo, it belongs in project-scoped `.mcp.json`.
- **Committing a literal API token into `.mcp.json`** — the most direct way to leak a credential into git history. `${VAR}` expansion exists precisely so the committed file never contains a secret.
- **Building a custom MCP server for GitHub or Jira integration** — solves the integration, but at unnecessary cost when a maintained community server already does the job. Reserve custom builds for workflows that are genuinely unique to your team.
- **Leaving MCP tool descriptions minimal and hoping the model "just knows" to prefer them** — the model has no way to know an MCP tool is more capable than Grep unless the description says so explicitly; a vague MCP description loses to a built-in tool the model already trusts.
- **Skipping resources and relying on the agent to "explore" with tool calls** — works, but burns exploratory tool calls rediscovering the same catalog every session. Exposing a content catalog as a resource turns repeated discovery into a single read.
