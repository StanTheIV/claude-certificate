# Integrating Claude Code into CI/CD Pipelines

## The `-p` (`--print`) flag: non-interactive mode

Claude Code's default interactive mode waits for you to type responses. Run it that way in a CI pipeline and the job hangs indefinitely, waiting for input that will never come — a classic symptom is logs showing Claude Code "waiting for interactive input" with no error, just a stuck job.

The fix is the `-p` (or `--print`) flag:

```bash
claude -p "Analyze this pull request for security issues"
```

This runs Claude Code in **non-interactive mode**: it processes the prompt, prints the result to stdout, and exits — no waiting for a human to respond. This is the only correct way to run Claude Code in an automated pipeline.

> **Exam trap:** setting an environment variable like `CLAUDE_HEADLESS=true`, or adding a `--batch` flag, or redirecting stdin from `/dev/null`, are all tempting-sounding fixes for a "hanging in CI" symptom — but `CLAUDE_HEADLESS` and `--batch` don't exist, and redirecting stdin is a Unix workaround, not Claude Code's non-interactive mode. `-p` / `--print` is the flag that actually exists and actually solves it.

## Structured output for CI: `--output-format json` and `--json-schema`

A CI pipeline usually needs to *parse* Claude's output programmatically — for example, to post each finding as a separate inline PR comment at a specific file and line. Free-form narrative text isn't machine-parseable.

```bash
claude -p "Review this PR" --output-format json --json-schema '{"type":"object", ...}'
```

- `--output-format json` returns the result as structured JSON instead of plain text.
- `--json-schema` additionally validates the output against a schema you provide, so downstream code can rely on the shape of the result (which fields exist, their types) rather than trying to parse loosely-structured prose.

The parsed JSON can then drive automation directly: posting inline PR comments with file path, line number, severity, and suggested fix as separate structured fields, instead of a human copying details out of a paragraph.

> **Key idea:** `--output-format json` alone gives you valid JSON; `--json-schema` on top of it guarantees that JSON matches a *specific shape* your downstream code expects. Use both together for CI automation that parses findings into individual fields.

## `CLAUDE.md` as CI context

A CI-invoked Claude Code run doesn't have the developer sitting next to it to explain project conventions — everything it knows has to come from what's loaded automatically. `CLAUDE.md` is the mechanism for giving that context: testing standards, fixture conventions, and review criteria that a project-level `CLAUDE.md` normally documents for human contributors work exactly the same way for CI runs.

Documenting these explicitly in `CLAUDE.md` — what makes a test valuable versus low-value, which fixtures already exist, what the team's review checklist actually checks for — directly improves the quality of CI-generated output. Without that context, a CI review or test-generation run has to guess at project-specific standards from the diff alone, which produces generic, less useful output (or output that contradicts standards a human reviewer would immediately flag).

## Session context isolation

A subtle but important limitation: **the same Claude Code session that generated a piece of code is less effective at reviewing that same code**, compared to an independent instance reviewing it fresh. The generating session already has a reasoning trail behind its choices — it's less likely to challenge decisions it just made, even when a fresh perspective would catch an issue.

The practical consequence for CI design: run code review as a **separate, independent instance**, not as a follow-up turn in the same session that produced the change. An independent reviewer has no stake in defending the prior reasoning, mirroring how human code review works — a second person, not the original author, is expected to catch what the author rationalized away.

> **Exam trap:** "have the same session double-check its own output before finishing" sounds like a reasonable review step, but it doesn't address the actual limitation — the session's own reasoning trail is exactly what makes it less likely to flag its own decisions. A genuinely independent instance is the fix, not an extra self-review pass in the same context.

## Avoiding duplicate and low-value output

Two recurring CI problems and their fixes:

**Duplicate review comments on re-runs.** When a PR gets new commits and the review re-runs, a naive approach re-reports every issue from scratch — including ones already fixed. The fix: include the **prior review's findings** in context when re-running, and instruct Claude to report only *new* or *still-unaddressed* issues. This keeps the review current without re-flagging fixed code.

**Duplicate or low-value test suggestions.** When generating new tests for a PR, Claude doesn't know what's already covered unless you tell it. The fix: provide the **existing test files** in context, so test generation can check what scenarios are already tested and focus on genuinely new coverage instead of re-suggesting cases the suite already handles.

Both fixes follow the same shape: the CI run is missing information a human reviewer would have had by default (what changed since last time, what's already tested), and providing that information directly — rather than adding more instructions asking Claude to "avoid duplicates" — fixes the root cause.

## Exam lens: why the distractors lose

- **`CLAUDE_HEADLESS=true`, `--batch`, or `stdin < /dev/null`** all lose to `-p` / `--print` — the first two are invented, and the stdin redirect is a shell workaround that doesn't address Claude Code's command syntax; the real problem has a real, documented fix.
- **Detailed prose formatting instructions ("format each finding as `[FILE:...] [LINE:...] ...`")** lose to `--output-format json` + `--json-schema` — prose-level formatting instructions are still probabilistic; the CLI flags guarantee parseable structure at the tooling level.
- **Having the same session review its own generated changes** loses to spinning up an independent review instance — self-review doesn't address session context isolation, the actual root cause of missed self-authored issues.
- **Re-running review with no memory of prior findings, then filtering duplicates afterward with a text-matching post-processor** loses to including prior findings in context and asking Claude to report only new/unresolved issues — a keyword-matching filter is a fragile workaround for something Claude can do directly when given the missing context.
- **Generating tests with no visibility into the existing suite, then filtering out anything that "sounds similar" afterward** loses to giving Claude the existing test files directly — it fixes the root cause (missing information) instead of patching the symptom after the fact.
- **Skipping `CLAUDE.md` in CI "since there's no developer to read it"** loses to documenting testing standards and fixture conventions there — CI runs read `CLAUDE.md` exactly like an interactive session does, and skipping it just means CI output has less project context than a human contributor would have had.

## Beyond the exam: Claude Code on GitHub in practice

> **Note (current docs):** This is practical background from the current Claude Code docs, beyond the exam guide. The exam tests the ideas in the earlier chunks, not these details.

**How the GitHub integration works.** The Claude Code GitHub Action (`anthropics/claude-code-action@v1`) runs Claude inside your own workflow. Run `/install-github-app` in Claude Code: it installs the Claude GitHub App, saves an `ANTHROPIC_API_KEY` secret and opens a PR with the workflow files. If the workflow has **no** `prompt` input, Claude waits for `@claude` in a comment. If it **has** a `prompt`, Claude runs on whatever event triggers the workflow. (A separate managed service, Code Review, reviews PRs without any workflow file.)

**Adjusting the automated review:**

| To change | Use |
|---|---|
| What Claude does | `prompt` input: plain text, or a skill such as `/code-review:code-review --comment ...` |
| When it runs | the workflow's `on:` events, e.g. `pull_request` with `types: [opened, synchronize]` |
| Turns, model, tools, extra instructions | `claude_args`: `--max-turns`, `--model`, `--allowedTools`, `--append-system-prompt` |
| Permission rules | `settings` input (JSON or a file path) |
| Project standards | `CLAUDE.md`, read on every run, so keep it short |
| Review-only rules (managed Code Review) | `REVIEW.md` at the repo root: severity, nit limits, paths to skip |

```yaml
- uses: anthropics/claude-code-action@v1
  with:
    anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
    prompt: "Review this PR. Report only new, unresolved issues."
    claude_args: "--max-turns 5"
```

**What loads at startup.** `CLAUDE.md` and `CLAUDE.local.md` from the working directory and every parent directory, plus their `@path` imports and any `.claude/rules/` files without `paths:`. Subdirectory `CLAUDE.md` files and path-scoped rules load later, when Claude reads matching files. Auto memory loads the first 200 lines (or 25KB) of `MEMORY.md`. For skills, only a **listing of names and descriptions** loads; the full `SKILL.md` body loads when the skill is used. MCP servers connect at startup, and hooks and plugins load too.

What makes startup heavy: many MCP servers, a long `CLAUDE.md` (the docs suggest under 200 lines; imports do **not** save context, because they load at launch too), and many skills. Fixes: move procedures into skills, move file-specific rules into path-scoped rules, set rarely used skills to `"name-only"` or `"off"` in `skillOverrides`, and check the result with `/context`. In a scripted `claude -p` run, the direct fix is `--bare`: skip the auto-discovery entirely and pass back in only what the run needs (below).

**Controlling a `claude -p` run.** By default, `-p` loads the same context as an interactive session: `CLAUDE.md`, skills, hooks in the project's `.claude/settings.json` and servers in `.mcp.json`. It does this with no trust dialog and no per-server approval, even in a folder you've never opened before.

**`--bare`: start from nothing.** It skips auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory and `CLAUDE.md`. Startup is faster, and the run behaves the same on every machine: a hook in a teammate's `~/.claude` or a server in the repo's `.mcp.json` never runs. Claude keeps the Bash, file read and file edit tools.

- **Auth:** bare mode never reads OAuth credentials or the keychain, so a subscription login doesn't work. Set `ANTHROPIC_API_KEY`, or put an `apiKeyHelper` in the `--settings` JSON.
- **No `CLAUDE.md`:** your project standards are not in context unless you pass them.
- **One exception:** skills in the `.claude/skills/` folder of a directory you pass with `--add-dir` still load.
- **Direction of travel:** the docs recommend `--bare` for scripts and SDK calls, and say it will become the default for `-p`.

Add back only what the run needs:

| To load | Flag |
|---|---|
| System prompt additions | `--append-system-prompt`, `--append-system-prompt-file` |
| Settings (permissions, `apiKeyHelper`) | `--settings` |
| MCP servers | `--mcp-config` |
| Custom subagents | `--agents` |
| A plugin | `--plugin-dir`, `--plugin-url` |

**Replacing vs appending the system prompt.**

| Flag | Effect |
|---|---|
| `--system-prompt "..."` | Replaces the entire default prompt |
| `--system-prompt-file <path>` | Replaces it with the file's contents |
| `--append-system-prompt "..."` | Adds text to the end of the default prompt |
| `--append-system-prompt-file <path>` | Adds the file's contents to the end |

- **Append is the usual choice.** Claude stays a coding agent and keeps the default prompt's tool guidance, safety instructions and coding conventions; you supply only what differs, such as "You are a security engineer. Review for vulnerabilities."
- **Replace only when the job isn't a coding assistant's job**, such as a non-coding agent in a pipeline nobody watches. Replacing drops *all* of the default prompt, including tool guidance and safety instructions, so you must supply whatever the task still needs.
- `--system-prompt` and `--system-prompt-file` can't be combined with each other. Either append flag can be combined with either replace flag.
- Conventions that should always apply belong in `CLAUDE.md`. In a `--bare` run, which skips `CLAUDE.md`, `--append-system-prompt-file` is how you pass them.

A scripted review that combines these:

```bash
git diff main | claude --bare -p "Review this diff"   --append-system-prompt-file ./review-rules.md   --allowedTools "Read" --output-format json
```

**Narrowing further** (with or without `--bare`):

- `--setting-sources user,project,local`: choose which settings files load.
- `--strict-mcp-config --mcp-config ./mcp.json`: use only these MCP servers.
- `--tools "Read,Edit"` limits which built-in tools exist; `--allowedTools` only pre-approves tools; `--disallowedTools "mcp__*"` removes all MCP tools.
- `--disable-slash-commands`: turns off all skills and commands.
