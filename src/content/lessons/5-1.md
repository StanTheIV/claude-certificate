# Manage Conversation Context to Preserve Critical Information

## Progressive summarization loses the numbers that matter

When a conversation gets long, systems often summarize older turns to save tokens. This is useful, but dangerous for precision. A summarizer tends to compress specific numbers, percentages, dates, and customer-stated expectations into vague language.

Imagine a support conversation: "Order ORD-67890, placed 2025-01-15, total $89.99, customer wants a full refund, not store credit." After two rounds of summarization this can degrade to: "Customer had an order issue and wants it resolved." The order ID, the date, the exact amount, and the explicit preference (refund, not credit) are all gone. If a later step in the workflow depends on the exact amount to approve a refund, the agent now has to guess or re-ask.

This matters most for **transactional facts**: identifiers, amounts, dates, statuses, and explicit customer requests. These are exactly the details a summary is most likely to blur, because a summarizer optimizes for a short, fluent paragraph, not for preserving every number.

> **Key idea:** Summarization is fine for narrative context ("customer was frustrated about a late delivery"). It is unsafe for facts that a downstream decision depends on ("refund amount: $89.99"). Keep those two kinds of information in different places.

The fix, covered in the next chunks, is to stop relying on the summarized history alone for facts that matter, and to still pass complete history to the API so the model has full conversational coherence.

## The "lost in the middle" effect

Even without summarization, long inputs have a second, separate problem. Models reliably attend to the **beginning** and the **end** of a long input, but are more likely to miss or under-weight information buried in the **middle**.

This shows up when an agent aggregates many pieces of content: a long list of tool results, a stitched-together research report, or a big pasted log file. If the one critical finding — a vulnerability, a contradictory data point, a blocking dependency — sits in the middle of ten sections, the model is statistically less likely to surface it in its final answer than if it sat at the top or bottom.

This is not a summarization problem; it happens even with the full, unsummarized input in context. It is a property of how long inputs are processed, and it means **where** you put information is a design decision, not an afterthought.

> **Exam trap:** "Use a model with a bigger context window" does not fix this. A bigger window lets you fit more in, but it does not change the attention pattern across the middle of that window. The fix is how you *organize* the input, not how much of it fits.

## Trimming verbose tool outputs before they accumulate

Tool results often return far more than an agent needs. A `lookup_order` call might return 40+ fields — shipping carrier metadata, internal warehouse codes, tax breakdowns — when only 5 are relevant to deciding whether a return is eligible: order ID, status, total, items, and `return_eligible`.

If every tool call's full result is appended to context, token usage grows disproportionately to the *relevance* of that data, not its size. Over a multi-turn conversation with several tool calls, this crowds out room for everything else, including the case facts that actually matter.

The fix is to trim tool outputs to relevant fields before they enter context, for example with a hook that runs right after the tool call:

```python
# PostToolUse hook: keep only relevant fields
@hook("PostToolUse", tool="lookup_order")
def trim_order_fields(result):
    return {
        "order_id": result["order_id"],
        "status": result["status"],
        "total": result["total"],
        "items": result["items"],
        "return_eligible": result["return_eligible"],
    }
```

This is a programmatic, deterministic trim — it runs the same way every time, unlike asking the model to "please summarize the order details" in the prompt, which is probabilistic and can drop the wrong field.

## The persistent case-facts block

Because summarized history is unreliable for precise facts, keep transactional facts in a **separate, structured block** that is included in full in every prompt, outside whatever summarization happens to the conversational history:

```
=== CASE FACTS (updated whenever a new fact appears) ===
Customer ID: CUST-12345
Order ID: ORD-67890
Order Date: 2025-01-15
Order Amount: $89.99
Issue: Damaged item on delivery
Customer Request: Full refund
Status: Pending manager approval
===
```

This block is small, so it costs little in tokens, and it is never summarized — it is extracted and rewritten explicitly whenever a new fact appears. For sessions that cover multiple issues (a customer asks about two different orders in one conversation), extract and persist the structured data for each issue into its own entry in this layer, rather than letting facts from different issues blur together in one summarized narrative.

> **Key idea:** Treat facts and narrative as two different context layers. Narrative can be summarized; the facts block cannot — it is always included verbatim.

## Position-aware ordering and structured handoffs between agents

Two more techniques counteract the problems above, both about *where* and *how* information is presented, not how much of it there is.

**Position-aware input.** When you aggregate results — from multiple tool calls, multiple subagents, or a long document — put the key findings summary **first**, then the detailed results, organized under explicit section headers so the reader (human or model) can navigate directly to a section instead of relying on serial attention across the whole block:

```
[KEY FINDINGS — at the top]
Found 3 critical vulnerabilities...

[DETAILED RESULTS — organized by section]
=== File auth.ts ===
...
=== File database.ts ===
...
```

**Structured handoffs for limited-budget downstream agents.** When one agent's output becomes another agent's input, and the downstream agent has a limited context budget, do not hand it verbose content and reasoning chains. Require the upstream agent to output structured data instead: key facts, citations, relevance scores, and metadata such as dates and source locations. This keeps the downstream agent's context small and gives it exactly what it needs to synthesize correctly, without re-deriving conclusions from raw text.

## Exam lens: why the distractors lose

- **"Use a bigger context window" vs. reorganize the input** — a larger window does not fix lost-in-the-middle; the deciding principle is that attention position, not window size, causes the effect.
- **"Let the model summarize the order details in the prompt" vs. a programmatic trim** — a prompt instruction to trim fields is probabilistic and can vary call to call; a hook that trims deterministically is repeatable. Deterministic guarantees win when a downstream decision depends on the exact fields.
- **"Rely on the running conversation summary for the refund amount" vs. a persistent case-facts block** — summarization is designed to compress, so numbers are exactly what it is unsafe to trust it with. A separate, always-included facts block avoids the risk entirely.
- **"Drop old history to save tokens" vs. passing complete history** — omitting history for cost reasons breaks conversational coherence; the correct trade-off is to *trim what's irrelevant* (verbose tool fields), not to drop conversation turns wholesale.
- **"Have the downstream agent read the upstream agent's full reasoning chain" vs. structured output** — when the downstream agent has a limited budget, verbose reasoning is the wrong shape of input; structured facts and citations are cheaper and more reliable to consume.
