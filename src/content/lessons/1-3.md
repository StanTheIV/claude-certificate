# Configure subagent invocation, context passing, and spawning

## The `Task` tool and `allowedTools`

Subagents aren't invoked by magic — the coordinator spawns them by calling the **`Task` tool**, exactly like it would call any other tool. This has a direct configuration consequence: for a coordinator to be able to delegate at all, its `allowedTools` (or `allowed_tools`) list **must include `"Task"`**, alongside whatever domain tools it needs directly.

```python
coordinator_agent = AgentDefinition(
    name="research_coordinator",
    allowed_tools=["Task", "get_customer"],  # "Task" enables spawning subagents
)
```

If `"Task"` is missing from `allowedTools`, the coordinator can reason about delegating work, but it has no mechanism to actually spawn a subagent — this is a common configuration bug to recognize on the exam: a coordinator that "should" delegate but structurally can't.

## `AgentDefinition`: configuring each subagent

Each subagent type is configured through an `AgentDefinition`, which typically specifies:
- **`name` / `description`** — identifies the agent and what it's for (used for routing/selection)
- **`system_prompt`** — instructions defining the subagent's role, expertise, and behavior
- **`allowed_tools`** — the specific tools this subagent may call (principle of least privilege — a synthesis subagent doesn't need refund tools, a document-analysis subagent doesn't need `Task` unless it spawns its own subagents)

```python
research_agent = AgentDefinition(
    name="web_search",
    description="Searches the web for sources on a given subtopic",
    system_prompt="You are a research assistant specializing in web search...",
    allowed_tools=["web_search"],
)
```

> **Key idea:** Tool restrictions per subagent aren't just security hygiene — they're part of the architecture. A tightly scoped `allowed_tools` list is what keeps a subagent from doing more (or less) than its assigned role.

> **Note (current docs):** The current Agent SDK reference names the `AgentDefinition` fields `prompt` (not `system_prompt`) and `tools` (not `allowed_tools`). `allowed_tools` / `allowedTools` is the option on the *calling* agent that must include `"Task"` to permit spawning subagents at all. Study materials (and this lesson) use `system_prompt`/`allowed_tools` for both, so recognize either naming.

## Subagents do not inherit context automatically

This is the single most tested fact in this task statement: **subagents run with isolated context.** A subagent does not automatically see the coordinator's conversation history, prior tool results, or anything else from the parent session. Every subagent invocation effectively starts from a blank slate except for what you put in its prompt.

```
# Bad — the subagent has no idea what was already found
Task: "Analyze the document."

# Good — full context explicitly included in the prompt
Task: "Analyze the following document for claims relevant to 'AI adoption in healthcare.'
Document: [full document text]
Prior web search findings: [search results, with source URLs]
Output format: return each claim with its source and a confidence label."
```

If a subagent needs to know what another subagent already found, the coordinator must copy those findings — in full, not by reference — directly into the new subagent's prompt. There is no shared memory between subagent invocations to fall back on.

> **Exam trap:** A scenario describing a subagent that "should have known" something a sibling subagent found, but didn't, is testing this exact fact. The fix is never "give the subagents shared state" (not how the architecture works here) — it's "include the finding explicitly in the next prompt."

## Structured formats to preserve attribution

When passing findings between agents, don't collapse everything into a single blob of prose — use a **structured format that separates content from metadata**: the claim/finding itself, separately from its source URL, document name, page number, or publication date. This matters because downstream agents (especially synthesis) need to cite sources accurately, and prose blobs make it easy to lose track of which fact came from where.

```json
{
  "finding": "Adoption of AI diagnostics grew 34% year over year",
  "source_url": "https://example.org/report",
  "document_name": "2025 Healthcare AI Report",
  "page": 12
}
```

Passing this structured object into the synthesis subagent's prompt (rather than a paraphrased sentence) preserves attribution all the way through to the final report.

## Parallel spawning: multiple `Task` calls in one response

A coordinator can spawn several subagents **concurrently** by emitting multiple `Task` tool calls within a *single* response, rather than issuing them one at a time across separate turns:

```
# One coordinator response contains:
Task 1: "Search for academic sources on X"
Task 2: "Analyze document Y"
Task 3: "Search for industry news on Z"
# All three execute in parallel
```

Doing this sequentially (one `Task` call, wait for the result, then the next `Task` call) works but adds latency for no benefit when the subtasks don't depend on each other's output. Whenever subtasks are independent, batching the `Task` calls into one coordinator response is the more efficient design.

## Goal-and-criteria prompts over step-by-step procedures

When writing the coordinator's own prompt (and the prompts it constructs for subagents), specify **research goals and quality criteria** rather than a rigid, step-by-step procedure. A goal-oriented prompt ("find at least three independent sources covering both benefits and risks, and flag any contested claims") lets a subagent adapt its approach to what it actually finds. An overly procedural prompt ("first search X, then search Y, then summarize in exactly three bullets") can leave the subagent unable to adapt when reality doesn't match the anticipated script.

Related but distinct: **fork-based session management** lets you branch from a shared analysis baseline to explore divergent approaches in parallel (e.g., comparing two research strategies starting from the same initial findings) — this is a session-level tool, covered in depth in Task Statement 1.7, but it's worth knowing it exists as part of the subagent/session toolkit.

## Exam lens: why the distractors lose

- **Coordinator lacking `"Task"` in `allowedTools`** — a coordinator prompt can say "delegate to subagents" all day, but without `"Task"` permitted, there's no mechanism to do so; this is a configuration gap, not a prompting gap.
- **Assuming subagents inherit parent context** — the exam consistently tests this misconception; the fix is always explicit inclusion in the prompt, never "shared memory" or "automatic inheritance" (neither exists in this architecture).
- **Passing findings as unstructured prose vs. structured content+metadata** — prose is fine for a human summary but loses the source/document/page attribution a synthesis step needs; structured data wins when provenance matters.
- **Sequential `Task` calls across turns vs. parallel `Task` calls in one response** — sequential calls work but cost latency; when subtasks are independent, parallel spawning in a single response is strictly better.
- **Rigid step-by-step subagent prompts vs. goal-and-criteria prompts** — procedural prompts break when reality diverges from the anticipated steps; goal-oriented prompts let the subagent adapt while still hitting the actual objective.
- **Deciding principle:** every subagent capability question resolves to "what's explicitly in the `Task` prompt and the `AgentDefinition`?" — nothing is inherited, shared, or assumed.
