# Distributing Tools and Configuring Tool Choice

## Fewer tools, better decisions

It is tempting to give every agent access to every tool "just in case." In practice, this makes tool selection *worse*, not more flexible. Every additional tool is another option the model has to weigh on every turn, and past a certain point the marginal tool doesn't add capability so much as it adds confusion between near-equivalent choices.

The rule of thumb that shows up repeatedly in production systems: an agent that needs 4–5 tools to do its job reliably will select among them well. The same agent given 18 tools — most of them irrelevant to its actual role — selects less reliably, even for the tools it genuinely needs. The extra tools are not neutral; they are decision-complexity overhead on every single turn.

This has a direct design consequence: a subagent's tool list should not be "everything the system has," it should be "exactly what this role needs." A synthesis agent that combines findings from other agents does not need a web-search tool — and if you give it one anyway, it will sometimes reach for it, even when that's not its job.

> **Key idea:** Tool count is a reliability variable, not just a capability variable. More tools on an agent doesn't just add options — it degrades selection among all of them, including the ones it actually needs.

## Scoping tools to an agent's role

Agents that have tools outside their specialization tend to misuse them — not because the model is careless, but because a tool that's present in the list is implicitly an invitation to consider using it. A synthesis agent with web-search access will sometimes do its own research instead of asking the coordinator to delegate it, duplicating work and stepping outside its intended role.

The fix is scoped tool access: give each agent only the tools its role actually requires. In a multi-agent research system, that typically means:

- The **web search agent** gets search and fetch tools, not synthesis or reporting tools.
- The **document analysis agent** gets document-parsing tools, not web search.
- The **synthesis agent** gets tools for combining and citing findings, not tools for going out and gathering new ones.
- The **report generator** gets formatting/output tools, not research tools.

This isn't about distrust of the model — it's about removing the *opportunity* for role drift. An agent literally cannot misuse a tool it was never given.

## Constrained tools beat generic ones

Scoping isn't only about which tools an agent has — it's also about how permissive each individual tool is. A generic `fetch_url` tool that can retrieve *any* URL gives an agent far more surface area than it usually needs, including the ability to fetch documents that were never validated as legitimate sources.

Replacing it with a constrained tool like `load_document` — one that validates the URL against an allowed pattern or a known document registry before fetching — keeps the same core capability (get document content) while removing the failure modes that come with an unconstrained fetch. The agent can still do its job; it just can't wander outside the boundary the tool enforces.

> **Exam trap:** Giving an agent "more tools, more general-purpose" looks like flexibility, but it's usually the wrong trade. A narrower, purpose-built tool with a validated contract is both safer and easier for the model to select correctly than a broad tool that "could" be used a dozen ways.

## Scoped cross-role tools for high-frequency needs

Strict role separation is the default, but it isn't absolute. Some cross-role needs happen so often that routing every instance through the coordinator adds real overhead without adding safety.

Consider a synthesis agent that frequently needs to verify a specific claim (a date, a name, a statistic) while combining findings. If every verification goes: synthesis → coordinator → web search agent → coordinator → synthesis again, that's 2–3 extra round trips per verification, and it adds up in both latency and cost. If most of these checks (say, 85%) are simple, low-risk fact lookups, the proportionate fix is to give the synthesis agent a single, narrow `verify_fact` tool scoped to exactly that: quick lookups, nothing else. The remaining, more complex verifications still route through the coordinator to the full web search agent.

This is the principle of least privilege applied precisely: the synthesis agent gets *just* the capability that covers its common case, not general web-search access. It preserves the coordinator-mediated path for anything that doesn't fit the narrow tool's scope.

## tool_choice: auto, any, or forced

Once an agent has the right tools, `tool_choice` controls how the model is allowed to use them on a given turn:

| Value | Behavior | When to use |
|---|---|---|
| `{"type": "auto"}` | The model decides whether to call a tool or answer in text | Default — most conversational and exploratory turns |
| `{"type": "any"}` | The model **must** call some tool (any of the available ones) | You need guaranteed structured output, but any of several tools would satisfy it |
| `{"type": "tool", "name": "extract_metadata"}` | The model **must** call this specific tool | You need to guarantee a specific first action, e.g. forcing `extract_metadata` before enrichment tools run |

`"any"` is the right call when you don't care *which* tool fires, only that the model doesn't drift into a plain-text response when you need a structured result. Forced selection (`{"type": "tool", "name": ...}`) is for when the order matters — you need step one to be a specific tool, then you process the result and let the model choose (often back to `"auto"`) for subsequent steps in a follow-up turn.

## Exam lens: why the distractors lose

- **Giving an agent broad or full access "to be safe"** — looks flexible, but it's the direct cause of cross-specialization misuse and degraded selection reliability. Scoped access isn't a restriction for its own sake; it's what keeps an agent's tool list matched to its job.
- **Batching all verification needs and sending them to the coordinator at once** — sounds efficient, but it creates blocking dependencies when later steps in the same pass depend on facts verified earlier. A scoped `verify_fact` tool avoids the round trip *and* the ordering problem.
- **Giving the synthesis agent full web-search access "since it needs some of it anyway"** — over-provisions for the 85% simple case by granting capability sized for the 15% complex case. It breaks separation of concerns and reopens the misuse risk role-scoping was meant to prevent.
- **Speculative caching to "anticipate" what a downstream agent might need** — sounds proactive, but it can't reliably predict actual verification needs, and unused cached context is wasted cost. A scoped tool that answers on demand is simpler and more reliable than trying to guess in advance.
- **Using `tool_choice: "any"` when you actually need a specific tool called first** — guarantees *a* tool call, but not the *right* one in the *right order*. When sequencing matters (metadata extraction before enrichment), only forced selection on the specific tool name gives that guarantee.
