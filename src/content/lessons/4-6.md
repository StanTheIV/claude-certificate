# Multi-Instance and Multi-Pass Review Architectures

## Why self-review has a ceiling

Asking the same Claude instance that just generated a piece of code, or produced an extraction, to also review its own output for problems has a structural limitation: that instance still carries the **reasoning context** from generation. It remembers *why* it made each choice, and that memory makes it less likely to seriously question those same choices in the same session — a design that looked reasonable during generation still looks reasonable a moment later to the same reasoning trace, even when an issue is actually present.

This isn't fixed by asking harder. A prompt like "now review your own code critically" or turning on extended thinking for the review step doesn't remove the underlying problem: the model is still reasoning from the same starting context that produced the original output, just with more tokens spent restating the same assumptions.

> **Exam trap:** "Add a self-review instruction" or "use extended thinking for the review pass" both sound like they add rigor, but neither removes the shared reasoning context that limits self-review in the first place.

## Independent instances catch what self-review misses

A **second, independent Claude instance** — one that receives the code or output to review but *not* the first instance's reasoning trace or conversation history — is structurally better positioned to catch subtle issues. It approaches the artifact fresh, without an existing narrative about why each decision was correct, so it's free to question choices the generating instance had already reasoned itself into accepting.

In practice this means: generate with one session, then open a **new session** (or a subagent with no shared context) and hand it only the artifact to review — the code, the extracted data, the report — not the chain of reasoning that produced it. This is a concrete architectural decision, not a prompting trick: it requires actually isolating context, not just asking the same context to "look again."

> **Key idea:** Self-review instructions and extended thinking both still run inside the generator's own reasoning context. An independent instance without that context is what actually catches subtle issues self-review tends to miss.

## Multi-pass review: per-file, then integration

A single review pass over a large pull request — say 14 files — tends to produce inconsistent results: deep, careful comments on some files and superficial ones on others, obvious bugs missed in the middle of the batch, and even contradictions, like flagging a pattern as a problem in one file while approving the identical pattern elsewhere in the same PR. This is **attention dilution**: spreading a fixed amount of analysis across too much material at once degrades the quality and consistency of each individual judgment.

The fix is to restructure the review into focused passes:

```
Pass 1 (per-file): analyze auth.ts alone -> local issues in auth.ts
Pass 1 (per-file): analyze database.ts alone -> local issues in database.ts
Pass 1 (per-file): analyze routes.ts alone -> local issues in routes.ts
...
Pass 2 (integration): given all files, analyze cross-file relationships
  -> issues like inconsistent types across module boundaries, circular
     dependencies, a function's contract changed in one file but not
     updated at its call sites in another
```

Splitting the work this way keeps each per-file pass focused enough to give every file the same depth of attention, while a separate integration pass specifically targets the class of bug that per-file analysis structurally cannot see — problems that only exist in how files interact.

> **Exam trap:** "Use a bigger model / larger context window so all files fit in one pass" is a common but incorrect fix — attention dilution is about analysis quality spread across content, not about whether everything technically fits in the context window. A larger window doesn't restore per-file depth.

## A wrong fix: majority-vote across full-PR passes

Running three independent full-PR review passes and only keeping findings that appear in at least two out of three might look like a way to filter out unreliable output, but it doesn't address attention dilution at all — each individual pass still analyzes all 14 files at once, with the same inconsistent depth problem. Worse, this approach actively **suppresses** real bugs that a single pass happens to catch: if a genuine issue is only noticed intermittently (which is exactly the attention-dilution symptom), requiring 2-of-3 agreement throws away a true finding just because it wasn't reproduced.

The correct fix targets the root cause — too much material analyzed in one undivided pass — not the symptom of inconsistent output across repeated full passes.

## Self-reported confidence for routing

A verification or review pass can be designed to have the model report a **confidence level alongside each individual finding**, not just an overall confidence for the whole review. This enables calibrated routing: high-confidence findings can be surfaced directly or even auto-applied, while low-confidence findings are routed to human review instead of being presented with the same weight as certain ones.

```json
{
  "finding": "Unhandled null case when order.customer is missing",
  "confidence": 0.4,
  "reasoning": "Only one example of this pattern seen; unclear if
                this path is reachable in production"
}
```

This is most useful when paired with the multi-pass and independent-instance patterns above: an independent verification pass, reviewing another instance's output fresh, can flag not just *what* looks wrong but *how sure it is*, giving the human reviewer a prioritized queue instead of an undifferentiated list of equally-weighted findings.

## Exam lens: why the distractors lose

- **Self-review instructions ("double-check your own work") as the fix for missed issues** — still runs inside the same reasoning context that produced the original output; an independent instance without that context is structurally better at catching subtle issues.
- **Extended thinking on the same instance instead of a second instance** — more reasoning tokens spent inside the same context doesn't remove the shared-context limitation; it's not a substitute for review by an instance without the generator's reasoning trace.
- **A bigger model or larger context window to fit all files in one pass** — misdiagnoses attention dilution as a capacity problem; the issue is inconsistent analysis depth across content, which per-file passes fix and a larger window does not.
- **Majority vote across repeated full-PR passes** — doesn't address the root cause (too much material per pass) and can actively suppress real bugs that only a subset of passes happen to catch.
- **Pushing the problem to developers ("split your PR into smaller submissions")** — shifts the burden without improving the review system itself; restructuring the automated review into per-file plus integration passes solves it without changing developer workflow.
- **Treating all findings as equally actionable with no confidence signal** — makes every finding compete for the same reviewer attention regardless of reliability; per-finding confidence enables routing high-confidence findings differently from low-confidence ones.
