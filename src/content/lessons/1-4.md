# Implement multi-step workflows with enforcement and handoff patterns

## Programmatic enforcement vs. prompt-based guidance

There are two fundamentally different ways to make an agent follow a required order of operations:

- **Prompt-based guidance:** you tell the agent, in the system prompt, "always verify the customer before processing a refund." The model usually complies.
- **Programmatic enforcement:** your code (a hook, a gate, a precondition check) refuses to let a downstream tool execute unless an upstream step has already completed successfully — regardless of what the agent "intends" to do.

The critical fact for the exam: **prompt instructions have a non-zero failure rate.** Even a very well-written instruction like "always call `get_customer` first" will occasionally be skipped by the model — production logs commonly show this happening in a small but real percentage of cases (e.g., "in 12% of cases the agent skipped verification"). For most workflow steps, an occasional miss is tolerable. But for some steps, it categorically isn't.

> **Key idea:** Ask "what happens if the model skips this step 1% of the time?" If the answer involves money, identity, or safety, you need a programmatic gate — not a stronger prompt.

## Deterministic gates for critical operations

When deterministic compliance is required — the textbook example is **verifying customer identity before any financial operation** — implement a programmatic prerequisite: a check that blocks the downstream tool call until the prerequisite tool has returned a verified result.

**Worked example:** block `process_refund` (and `lookup_order`) until `get_customer` has returned a verified customer ID. This isn't a prompt reminder — it's a gate in the tool-calling path that returns an error or refuses execution if the prerequisite hasn't run, no matter what the model "decided" to do.

```
if not context.has_verified_customer_id():
    reject_tool_call("process_refund requires a verified customer ID; call get_customer first")
```

This guarantees the ordering 100% of the time, closing exactly the gap that few-shot examples or stronger system-prompt wording cannot fully close.

> **Exam trap:** A tempting fix for "agent occasionally skips verification" is "add few-shot examples showing the agent always verifying first" or "strengthen the system prompt." Both are prompt-based and both leave a non-zero failure rate. When the stem mentions financial or identity consequences, the deterministic gate is the answer, not a better prompt.

## Decomposing multi-concern requests

Real customer messages often bundle several distinct issues in one message ("my order is late, AND I was charged twice, AND I want to change my address"). The effective pattern: **decompose the request into distinct items**, investigate each one — using shared context so you don't redo the same customer lookup three times — and only then **synthesize a single, unified resolution** back to the customer, rather than answering the first issue mentioned and dropping the rest.

Investigating the separate concerns can happen in parallel once the shared context (e.g., the verified customer record) is established, since the concerns are typically independent of each other.

## Structured handoff summaries for escalation

When a workflow needs to hand off to a human — because a case is too complex, a policy exception is needed, or the customer explicitly asked for a person — the human agent almost never has access to the full conversation transcript. They only see whatever summary the system hands them. That summary must therefore be **structured and self-contained**, typically including:

- Customer ID / identifying details
- Root cause of the issue
- Actions already taken (e.g., "verified via `get_customer`," "confirmed order via `lookup_order`")
- Recommended action (e.g., "approve full refund")
- Refund amount or other relevant figures
- Reason for escalation

A vague handoff ("customer is upset, please help") forces the human to re-investigate from scratch, defeating the purpose of the agent having done the work already. A complete structured handoff lets the human act immediately on the agent's findings.

> **Exam trap:** A distractor may propose escalating with just a generic message or the raw conversation transcript. A raw transcript technically contains the information, but it's not *structured* — the human still has to read and extract it. The tested skill is producing a compiled, field-by-field summary, not just forwarding everything.

## Exam lens: why the distractors lose

- **Stronger prompt / more few-shot examples vs. a programmatic gate** — when the scenario involves money or identity and cites a nonzero failure rate, only a deterministic gate closes it; prompt tuning only reduces the rate, it doesn't zero it out.
- **Over-engineered fixes (a routing classifier, new infrastructure) vs. a targeted precondition check** — if the actual problem is "step B ran before step A," a classifier that reroutes tool *availability* doesn't address *ordering* at all; it solves a different problem.
- **Answering only the first-mentioned concern vs. decomposing all concerns** — a multi-issue message deserves decomposition into separate, unified-into-one-response items, not a reply to only the most prominent complaint.
- **Escalating with the raw transcript vs. a compiled structured summary** — raw context passes the burden of extraction to the human; a structured handoff (customer ID, root cause, recommended action) is what lets a human act without re-investigating.
- **Deciding principle:** deterministic guarantee wins over probabilistic compliance whenever the failure mode has financial, identity, or compliance consequences — that's the line the exam draws consistently across this task statement.
