# Design task decomposition strategies for complex workflows

## Two decomposition philosophies

When you break a complex task into steps, there are two fundamentally different strategies, and choosing the wrong one for the situation is a common source of exam distractors:

- **Fixed sequential pipelines (prompt chaining):** the steps are decided in advance and always run in the same order, regardless of what's found along the way.
- **Dynamic adaptive decomposition:** the next subtask is generated based on what was actually discovered in the previous step — the plan adapts as you go.

Neither is universally "better." The right choice depends on whether the task's structure is predictable ahead of time.

> **Key idea:** Ask "do I already know every step this task needs before I start?" If yes, chain fixed steps. If the steps depend on what you find along the way, decompose dynamically.

## Prompt chaining: fixed pipelines

Use prompt chaining when the task structure is predictable and repeats the same shape every time — reviews that always follow the same template, extraction pipelines with a known sequence of stages, and so on.

```
Document -> Metadata extraction -> Data extraction -> Validation -> Enrichment -> Final output
```

**Worked example — multi-file code review:** for a pull request touching many files, split the review into a fixed sequence of passes:
1. **Per-file pass:** analyze each changed file individually for local issues (bugs, style, missed edge cases).
2. **Integration pass:** run a separate, focused pass examining relationships *between* files (inconsistent types across files, circular dependencies, contract mismatches).

This fixed two-stage structure is known in advance — you don't need to discover it as you go; every PR review needs a local pass and a cross-file pass.

**Why not review everything in one single pass instead?** Because processing many files together in one context causes **attention dilution**: some files get detailed analysis while others get superficial treatment, obvious bugs get missed under cognitive overload, and the model can give contradictory feedback (flagging a pattern as a problem in one file while approving the identical pattern elsewhere in the same PR). Splitting into a per-file pass plus a separate integration pass keeps depth consistent and still catches cross-file issues that a purely per-file approach would miss.

> **Exam trap:** "Use a larger-context model so it can hold all 14 files in attention at once" sounds like it should fix attention dilution, but it doesn't — dilution is a quality-of-attention problem, not a context-capacity problem. A bigger window doesn't make the model pay uniformly deep attention to every file within it.

## Dynamic adaptive decomposition

Use dynamic decomposition for open-ended, investigative tasks where the full scope genuinely isn't known up front — each step's findings determine what the next step should be.

**Worked example — "add comprehensive tests to a legacy codebase":**
1. First, **map the structure** (e.g., using `Glob`/`Grep` to find modules, existing test coverage, and dependencies) — you don't yet know which areas most need tests.
2. From that map, **identify high-impact areas** (e.g., three modules with zero test coverage, two with partial coverage, one of which handles payments — clearly higher risk than the others).
3. Build a **prioritized plan** based on what was found (start with the highest-risk, least-covered module).
4. **Adapt as new dependencies are discovered** mid-work — e.g., you find the payments module calls an external API, so you add a plan step to mock that API before writing tests for it, something you couldn't have planned before starting.

This task cannot be safely decomposed into a fixed pipeline up front, because you don't know the codebase's structure, risk areas, or hidden dependencies until you look. A team that tries to pre-write a fixed sequence of test-writing steps for an unfamiliar legacy codebase will either miss high-risk areas or hit unplanned dependencies mid-execution with no adaptation mechanism.

## Choosing the right pattern

| Signal in the scenario | Use |
|---|---|
| Task repeats the same known shape every time (reviews, extraction) | Prompt chaining (fixed pipeline) |
| Full scope is unknown until you start investigating | Dynamic adaptive decomposition |
| Findings at each step should influence what happens next | Dynamic adaptive decomposition |
| You need stability and reproducibility across runs | Prompt chaining |

> **Exam trap:** A scenario describing an open-ended investigation (e.g., "understand this unfamiliar legacy codebase and add tests where needed") paired with an option proposing a rigid, fully pre-specified sequence of steps is testing whether you recognize that the task's uncertainty requires adaptation — a fixed pipeline would either be wrong immediately or require constant manual re-planning.

## Exam lens: why the distractors lose

- **Fixed pipeline for an open-ended investigation** — pre-committing to a full sequence of steps for a task whose scope is unknown guarantees you'll miss discoveries made along the way; adaptive decomposition exists for exactly this situation.
- **Dynamic re-planning for a predictable, repeating task** — constantly re-deriving the plan for a task that always has the same shape (like a standard review template) adds overhead and inconsistency without benefit; a fixed chain is simpler and more reproducible.
- **Bigger context window as the fix for attention dilution** — dilution is about attention quality across many items, not about whether they technically fit in the window; the fix is splitting into focused passes, not expanding capacity.
- **Single-pass review over many files vs. per-file + integration passes** — a single pass over a large multi-file PR produces inconsistent depth and contradictory feedback; splitting into a local pass and a separate cross-file pass restores consistency.
- **Deciding principle:** match the decomposition strategy to how much of the task's shape you actually know in advance — fixed chains for known shapes, adaptive decomposition for genuine unknowns discovered along the way.
