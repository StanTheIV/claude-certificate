# Few-Shot Prompting for Consistent, Generalizable Output

## Why examples beat descriptions

Detailed written instructions can still leave room for interpretation. "Format findings clearly with location, issue, and severity" tells the model *what fields* to include but not exactly how to phrase them, how much detail to give, or how to handle edge cases. Two runs of the same prompt can produce differently shaped, differently detailed output even though both technically follow the instructions.

A **few-shot example** — 2 to 4 concrete input/output pairs embedded in the prompt — removes that ambiguity directly. Instead of describing the desired format in the abstract, you show it:

```json
{
  "location": "src/auth/login.ts:42",
  "issue": "SQL injection in the username parameter",
  "severity": "critical",
  "suggested_fix": "Use a parameterized query"
}
```

Given examples like this, the model doesn't have to guess how verbose the "issue" text should be or whether "suggested_fix" is optional — it can pattern-match structure and tone directly from what you showed it. For getting *consistently formatted, actionable output*, few-shot examples are the single most effective technique when detailed instructions alone haven't converged on a stable format.

> **Key idea:** When instructions alone produce inconsistent formatting, don't write a longer instruction — show 2-4 examples of the exact output you want.

> **Note (current docs):** Anthropic's current prompting guidance suggests 3-5 examples for best results in general-purpose prompts. The exam's target of 2-4 *targeted, ambiguous* examples is about picking quality over quantity for judgment-heavy tasks — both agree that a handful of well-chosen examples beats either zero or dozens of near-duplicates.

## Showing reasoning for ambiguous cases

Few-shot examples are most valuable when they resolve **ambiguity**, not when they just repeat the format for clear-cut cases. A strong example pairs a borderline input with the correct action *and a short rationale* for why that action was chosen over a plausible alternative:

```
Request: "My order is broken"
Action: Call get_customer -> lookup_order -> check status.
Rationale: "Broken" could mean a damaged item, a billing issue, or a
shipping problem — you need order details before you can act.

Request: "Get me a manager"
Action: Immediately call escalate_to_human.
Rationale: The customer explicitly asked for a human. Attempting to
resolve autonomously here would ignore a stated preference.
```

Notice the two examples don't just show different tool calls — they show *why* one ambiguous request needs investigation while another needs immediate escalation, even though both are phrased as short, vague complaints. Two to four such examples, chosen to be genuinely ambiguous (not just simple lookups), teach the model the underlying decision logic rather than a lookup table of literal phrases.

## Generalization, not memorization

A common misconception is that few-shot examples only help the model handle the exact cases shown. In practice, well-chosen examples teach the model to **generalize the underlying judgment** to novel inputs it has never seen. If your examples show the reasoning for escalating an explicit request for a human versus investigating a vague complaint, the model can apply that same reasoning to a third, differently worded request it hasn't seen before — "let me talk to someone in charge" — without a matching example for that exact phrase.

This generalization is why 2-4 *targeted*, ambiguous examples usually outperform a much longer list of near-duplicate examples: diversity in what makes each case ambiguous teaches the decision principle, while many similar examples just teach one narrow pattern more strongly.

> **Exam trap:** "Add ten more few-shot examples to cover more cases" is rarely the fix when 2-4 well-chosen examples already exist. The model already generalizes from targeted examples — more near-duplicate examples add cost without adding new judgment.

## Separating acceptable patterns from real issues

Few-shot examples are also the most direct way to cut false positives in a review or classification task: show the model a pattern that looks suspicious but is acceptable, next to a genuinely problematic variant of the same pattern.

```
// Acceptable (do not flag):
const items = data.filter(x => x.active);

// Problem (flag):
const items = data.filter(x => x.active == true); // use strict equality (===)
```

Both lines look similar at a glance, which is exactly why a written rule like "flag loose comparisons" can misfire on `x.active` when it's actually a plain boolean filter. Showing the acceptable/problem pair side by side teaches the model the actual distinguishing detail, reducing false positives on the acceptable pattern while still catching the real issue — the same generalization benefit as the ambiguous-request examples above.

## Reducing hallucination in extraction

For extraction tasks, few-shot examples reduce a specific failure mode: the model inventing a plausible-looking value instead of correctly parsing an unusual source format. This shows up most with informal or non-standard inputs — measurements, dates, or document structures that vary between sources:

```
Text: "about two handfuls of rice"
-> {"amount": "~100g", "original_text": "two handfuls", "precision": "approximate"}

Text: "a pinch of salt"
-> {"amount": "~1g", "original_text": "a pinch", "precision": "approximate"}
```

Written rules struggle to cover the full range of informal phrasing ("a splash of", "a couple of", "roughly a cup"), so the model may guess or fabricate a value without a concrete anchor. Examples covering a few representative informal patterns let the model generalize a sensible approach — extracting an approximate quantity and preserving the original text — to phrasing it hasn't seen.

The same technique applies to document structure: showing one example with inline citations and one with a bibliography teaches the model to detect and extract from both formats correctly, instead of only recognizing whichever format happened to be described in the instructions.

## Exam lens: why the distractors lose

- **Longer, more detailed written instructions instead of examples** — when instructions alone have already produced inconsistent output, adding more prose is unlikely to converge the format; showing 2-4 concrete examples is the more effective fix.
- **A huge example set ("more examples always help")** — many similar examples teach one narrow pattern strongly rather than the underlying judgment; a smaller set of *targeted, ambiguous* examples with reasoning generalizes better.
- **Examples with no rationale shown** — an example that only shows input -> output without the reasoning for ambiguous cases teaches the format but not the judgment, so novel ambiguous cases are handled inconsistently.
- **Assuming the model only repeats seen cases ("few-shot won't help with new phrasing")** — this underestimates generalization; well-chosen examples transfer the decision principle to inputs that don't literally match any example.
- **Fixing extraction hallucination with a stricter schema alone** — a schema (required fields, enums) constrains the *shape* of the output but doesn't teach the model how to interpret unfamiliar phrasing; few-shot examples address the interpretation problem directly.
- **Picking easy/unambiguous examples** — examples that aren't actually ambiguous don't teach a new decision boundary; the value comes from examples chosen specifically at the edge cases where judgment is needed.
