# Path-Specific Rules for Conditional Convention Loading

## The `paths:` frontmatter mechanism

`.claude/rules/` files can carry YAML frontmatter with a `paths` field containing glob patterns. When present, that rule file becomes *conditional*: it only loads when Claude is editing a file that matches one of the patterns.

```yaml
---
paths: ["src/api/**/*"]
---

For API files, use async/await with explicit error handling.
Each endpoint must return a standard response wrapper.
```

```yaml
---
paths: ["**/*.test.tsx", "**/*.test.ts"]
---

Tests must use describe/it blocks.
Use data factories instead of hardcoding.
Do not mock the database — use a test database.
```

Compare this to a plain `.claude/rules/` file from the previous lesson (no `paths:` field): that loads unconditionally, the same way project `CLAUDE.md` does. Adding `paths:` is what turns a rule file from "always loaded" into "loaded only when relevant."

## Why conditional loading matters

A rule that only applies to Terraform files doesn't need to be in context while Claude is editing a React component. Loading it anyway wastes tokens and dilutes the context with instructions that don't apply to the current work.

Path-scoped rules solve this by activating **only when editing a matching file**:
- Claude opens `src/api/orders.py` → the `paths: ["src/api/**/*"]` rule loads.
- Claude opens `src/components/Button.tsx` → that rule does not load; only rules matching `.tsx` files do.

This reduces irrelevant context and keeps the token budget focused on what's actually relevant to the file being touched. On a large codebase with many topic-specific conventions (API layer, database layer, frontend components, infrastructure-as-code), this is the difference between a lean, targeted context and a bloated one that repeats conventions the current task doesn't need.

> **Key idea:** `paths:` frontmatter is a token-budget and relevance tool, not a security or enforcement tool — it changes *when* the guidance is shown, not whether Claude can act outside of it.

## Worked example: conventions scattered across the codebase

Suppose a codebase has distinct areas with different conventions — React components use hooks, API handlers use async/await, database models follow a repository pattern — and test files are scattered *throughout* the codebase next to the code they test (`Button.test.tsx` beside `Button.tsx`, `orders.test.py` beside `orders.py`, and so on). You want every test file to follow the same testing conventions, no matter which directory it lives in.

A directory-level `CLAUDE.md` can't do this cleanly: it's bound to one directory, and test files aren't confined to one directory — they're spread across dozens of folders alongside the code they cover. You'd need a duplicate `CLAUDE.md` in every folder that contains a test file, an unmaintainable approach.

A `.claude/rules/testing.md` file with `paths: ["**/*.test.tsx", "**/*.test.ts", "**/*.test.py"]` solves it in one place: the glob matches test files *by name pattern*, regardless of which directory they're in. One file, one source of truth, automatically applied everywhere a matching file is touched.

This gives a general decision rule: if a convention applies to files that live in **one place**, a directory-level `CLAUDE.md` in that folder is simplest. If a convention applies to files **identified by type or naming pattern, scattered across many directories**, a `.claude/rules/` file with `paths:` glob matching is the maintainable choice — one file instead of many duplicated ones, and it stays correct even as new matching files are added anywhere in the tree.

## Glob patterns by file type, not location

Because `paths:` uses glob patterns, you can target files by extension or naming convention across the entire codebase:

| Pattern | Matches |
|---|---|
| `terraform/**/*` | Everything under the `terraform/` directory, any depth |
| `**/*.test.tsx` | Any `.test.tsx` file, anywhere in the repo |
| `src/**/*.py` | Any Python file under `src/`, any depth |

The `**` wildcard matches any number of intermediate directories, which is what makes "by file type regardless of location" possible. This is the core advantage over directory-bound CLAUDE.md files: a glob pattern follows the file type, a directory-level file follows the folder.

## Which configuration mechanism fits?

Claude Code offers several ways to shape behavior, and much of the exam's difficulty is picking the *right one* for a given situation — not because the others are broken, but because each is built for a different kind of guidance:

| Mechanism | When it loads | Best for | Guarantee |
|---|---|---|---|
| **CLAUDE.md** (user/project/directory) | Always, at session start (directory-level: when files there are touched) | Universal standards everyone needs every time | Probabilistic — Claude reads and tries to follow it |
| **`.claude/rules/` with `paths:`** | Only when editing a matching file | Conventions tied to a file type or pattern, spread across the codebase | Probabilistic, but scoped to relevant moments |
| **Skills (`.claude/skills/`)** | On demand — invoked by name or by Claude when the task matches | Specific, occasionally-needed workflows (release checklist, migration helper) | Probabilistic, and only runs when invoked |
| **Hooks** (e.g. `PreToolUse`) | On a fixed lifecycle event, every time, regardless of what Claude decides | Rules that must hold 100% of the time (blocking an action above a dollar threshold) | **Deterministic** — code runs, not a suggestion |
| **Settings permissions (`permissions.deny`, etc.)** | Enforced by the client on every matching tool call | Blocking specific tools, commands, or paths outright | **Deterministic** — enforced regardless of what Claude decides |

The first three are all *context* — they shape what Claude reads and how it's likely to behave, with no hard guarantee. The last two are *enforcement* — they run outside the model's control. When a rule is a strong preference, use CLAUDE.md, rules, or a skill. When a rule must never be violated (financial limits, destructive commands, compliance), a probabilistic instruction is the wrong tool no matter how clearly it's worded — that calls for a hook or a permission rule.

> **Exam trap:** a question describing a rule that must hold with zero exceptions, answered with "add stronger wording to CLAUDE.md" or "add a `.claude/rules/` file with clear instructions," is testing whether you know that *no* prompt-based mechanism gives a 100% guarantee. Only code-level enforcement does.

## Exam lens: why the distractors lose

- **A directory-level `CLAUDE.md` for a convention that spans scattered files** (like all test files) loses to a `paths:`-scoped rule — you'd need to duplicate the file in every directory that ever contains a matching file, and it silently misses new locations.
- **Consolidating all conventions into one root `CLAUDE.md` under different headers** loses to `paths:`-scoped rules — Claude has to infer which section applies from context, which is unreliable, versus the deterministic glob match that only loads the relevant section.
- **A skill for each code area's conventions** loses when the requirement is "automatically applied based on file path" — skills require invocation (explicit or inferred from the task description); they don't guarantee loading just because a matching file is opened.
- **"Just write the rule with very specific wording"** loses when the actual problem is *scope*, not clarity — no amount of rewording fixes a directory-bound file's inability to reach files in other directories.
- **Using a hook to inject conventions on every file open** is over-engineered for guidance that isn't a hard rule — `paths:` rules already solve conditional loading without custom enforcement code.
