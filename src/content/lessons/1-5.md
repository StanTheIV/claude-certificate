# Apply Agent SDK hooks for tool call interception and data normalization

## What hooks are: intercepting the agent lifecycle

**Hooks** are callback functions the Agent SDK runs at specific points in the agent's execution, letting your code inspect, transform, or block what's happening — deterministically, in code, rather than by hoping the model behaves a certain way. Two hook points matter most for this task statement:

- **`PostToolUse`** fires after a tool has executed and returned a result, *before* that result reaches the model. It lets you transform the tool's output.
- A **tool-call interception hook (`PreToolUse`)** fires *before* a tool call executes, letting you inspect the requested call and block or redirect it before it ever runs.

> **Key idea:** A `PostToolUse` hook changes what the model *sees* after a tool ran. An interception hook changes whether a tool call happens *at all*. Both are code, not prompts — both are deterministic.

## `PostToolUse`: normalizing heterogeneous data

Different backend systems — especially when you're integrating multiple MCP tools — often return the same kind of information in inconsistent formats: one tool returns a Unix timestamp, another returns ISO 8601, a third returns a numeric status code that means something different from the first tool's status code. If you hand all of this directly to the model, it has to guess at meaning and can misinterpret values.

A `PostToolUse` hook solves this by normalizing tool output before the model ever processes it:

```python
# PostToolUse hook: normalize heterogeneous date formats from different MCP tools
def normalize_dates(tool_result):
    # Unix timestamp -> ISO 8601
    # "Mar 5, 2025" -> "2025-03-05"
    return normalized_result
```

This is a data-quality fix applied once, in code, rather than asking the model to "remember" to convert formats correctly on every single turn — which is both wasted reasoning effort and an unreliable one.

## Interception hooks: enforcing compliance deterministically

The second hook pattern (`PreToolUse`) intercepts an **outgoing tool call** — a request the model is *about* to make — and blocks it if it violates a business rule, optionally redirecting to an alternative workflow.

**Worked example:** block any `process_refund` call where the requested amount exceeds $500, and redirect that case to a human-escalation workflow instead of letting the refund tool execute.

```python
# Intercept outgoing tool calls before they execute
def enforce_refund_limit(tool_call):
    if tool_call.name == "process_refund" and tool_call.args.amount > 500:
        return redirect_to_escalation(tool_call)
```

This is functionally similar to the "programmatic prerequisite gate" from Task Statement 1.4 (blocking `process_refund` until `get_customer` has run) — both are enforcement points in the tool-calling path. The hook mechanism is how you implement that kind of gate in the Agent SDK: the callback receives the proposed call before execution and can allow, block, or redirect it.

## Hooks vs. prompt instructions: the core distinction

| | Hooks | Prompt instructions |
|---|---|---|
| Guarantee | Deterministic — the check runs in code, every time, with no exceptions | Probabilistic — the model usually complies, but not always |
| Best for | Financial operations, compliance rules, identity checks, data normalization that must be consistent | General preferences, tone, formatting suggestions, "soft" recommendations |
| Failure mode if wrong choice | (using a prompt where a hook was needed) silent, occasional violations that slip through | (using a hook where a prompt was fine) unnecessary engineering overhead for a low-stakes preference |

The rule the exam wants you to apply: **choose hooks over prompt-based enforcement whenever business rules require guaranteed compliance.** If a question describes a compliance rule with real consequences (money, policy violations, data integrity) and asks how to *guarantee* it's followed, the answer involves a hook — not a more emphatic instruction.

> **Exam trap:** "Add a strongly worded rule to the system prompt: never approve refunds over $500" sounds like it addresses the same problem as an interception hook. It does not provide the same guarantee. If the question stem emphasizes needing this rule to *always* hold, prompt wording is a worse answer even if it usually works.

## Exam lens: why the distractors lose

- **Asking the model to remember format conversions vs. a `PostToolUse` normalization hook** — relying on the model to convert Unix timestamps or status codes correctly every turn is unreliable and wastes reasoning; a hook does it once, consistently, in code.
- **A strongly worded prompt rule vs. an interception hook for a hard compliance limit** — both often work in testing; only the hook guarantees the $500 threshold is never silently exceeded in production.
- **Blocking silently vs. blocking-and-redirecting** — a hook that just rejects a policy-violating call without redirecting to an alternative (like escalation) leaves the agent stuck with no path forward; the tested pattern explicitly redirects.
- **Using a hook for a low-stakes stylistic preference** — this is over-engineering; hooks are for guarantees that matter, not for tone or formatting nudges that a prompt handles fine.
- **Deciding principle:** if the consequence of an occasional model slip is acceptable, prompt-guide it; if it is not acceptable even once, hook it.
