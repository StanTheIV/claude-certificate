# Efficient Batch Processing Strategies

## The Message Batches API: what it trades away

The Message Batches API offers **50% cost savings** compared to synchronous calls, in exchange for giving up latency guarantees: batches can take **up to 24 hours** to process, with **no guaranteed SLA** on when within that window a given batch completes. Correlation between what you submitted and what came back is handled through a **`custom_id`** field you attach to each request, which appears alongside the matching result so you can match responses to the original inputs without relying on submission order.

A batch request also does **not support multi-turn tool calling** within a single request — it's one request in, one response out, with no mid-request loop where the API executes a tool call and waits for your tool result before continuing. If your workflow requires the model to call a tool, see the result, and then continue reasoning in the same turn, that has to run through the synchronous Messages API, not the batch endpoint.

```json
{
  "custom_id": "doc-invoice-2024-001",
  "params": {
    "model": "claude-...",
    "max_tokens": 1024,
    "messages": [{"role": "user", "content": "Extract data from: ..."}]
  }
}
```

> **Key idea:** Batches trade latency guarantees for cost. If a workflow can't tolerate "maybe up to 24 hours, no promises," it doesn't belong on the batch endpoint no matter how attractive the 50% savings look.

## Matching the API to the workflow's latency tolerance

The deciding question for batch vs. synchronous is not "is this workload large?" but "**can this workflow block a person waiting for the result?**"

| Workflow | API | Why |
|---|---|---|
| Pre-merge PR check | Synchronous | A developer is blocked waiting to merge; 24 hours (even "usually faster") is unacceptable |
| Overnight technical-debt report | Batch | Needed by morning; latency tolerance is hours, savings matter at volume |
| Weekly security audit | Batch | Not time-critical; ideal for the savings |
| Interactive code review in an IDE | Synchronous | Immediate response expected |
| Processing 10,000 documents for a data warehouse | Batch | Bulk, non-blocking; savings compound at volume |

A tempting but wrong middle ground is "switch to batch, but add a timeout that falls back to synchronous if it's taking too long." This sounds safe, but it adds real complexity (you now need to track and cancel in-flight batch jobs) for a workflow that should never have been on the batch path in the first place — the blocking workflow needed synchronous calls from the start.

> **Exam trap:** "Batch with a fallback timeout to synchronous" is over-engineering that still doesn't fix the underlying mismatch — a blocking, pre-merge-gate workflow needs a real latency guarantee, which only the synchronous API provides.

## Worked example: SLA math for submission cadence

Suppose a workflow must deliver results within a **30-hour SLA**, and the batch API can take up to **24 hours** to process a given submission. How often must you submit?

```
Available submission window = SLA - max processing time
                             = 30 hours - 24 hours
                             = 6 hours
```

If you submit only once, right at the start of the window, a batch that takes the full 24 hours still lands inside the 30-hour SLA — but only if you submit within the first 6 hours of the window opening. To keep a comfortable safety margin (and to smooth out load instead of always submitting at the last safe moment), many teams submit more frequently than the bare minimum — for example, every 4 hours — so that no single document ever waits close to the full 6-hour edge before its batch even starts.

This is a concrete skill the exam tests directly: given an SLA and the batch processing ceiling, compute the latest safe submission cadence, and recognize that "submit less often to save on overhead" can silently violate the SLA once you account for the full 24-hour worst case.

## Handling batch failures by custom_id

Real batches partially fail. Out of 100 submitted documents, 95 might succeed and 5 might fail — commonly because a document exceeded the model's context limit. The recovery pattern:

1. Identify the failed items by their **`custom_id`** (not by re-checking every result — only the ones flagged as errors)
2. Diagnose why each failed (e.g., document too large)
3. Modify only the failed inputs (e.g., **chunk** an oversized document into smaller pieces)
4. **Resubmit only the failed documents**, not the whole batch

Resubmitting the entire batch wastes the 50% savings you already captured on the 95 that succeeded, and risks reprocessing documents that don't need it. Because `custom_id` ties each result back to its source input, you can cleanly separate "already done" from "needs another pass" without re-running anything unnecessarily.

## Refine prompts on a sample before scaling up

Before submitting a batch of thousands of documents, run the extraction prompt against a **small representative sample** first, using the synchronous API for fast iteration. Check the failure rate and error types on the sample, refine the prompt (tighter criteria, better few-shot examples, clearer schema), and only then submit the full volume to the batch endpoint.

Skipping this step means discovering systematic prompt problems only after a large, slow, and costly batch run comes back with a high failure rate — at which point every failed document needs a full retry-and-resubmit cycle (another up-to-24-hour wait). A few minutes of fast, synchronous iteration on a sample is far cheaper than finding the same problem at scale after a full batch round-trip.

> **Key idea:** Batch is for scaling a prompt you already trust, not for discovering whether the prompt works. Validate on a sample synchronously first.

## Exam lens: why the distractors lose

- **Batch processing for a blocking pre-merge check "because of the cost savings"** — ignores that no-SLA, up-to-24-hour latency is incompatible with a workflow a developer is actively waiting on; the right first step is to keep pre-merge checks synchronous regardless of cost.
- **Batch with a synchronous fallback timeout** — adds real complexity (tracking and cancelling in-flight jobs) without fixing the mismatch; a blocking workflow should simply not be on the batch path.
- **Submitting once at the start of the SLA window "since 24 hours fits inside 30"** — technically fits the worst case exactly, but leaves no margin and doesn't smooth load; computing a real cadence (e.g., every 4 hours) inside the available submission window is the more robust approach the exam expects.
- **Resubmitting the entire batch after a partial failure** — wastes the savings already captured on the successful items and reprocesses documents that didn't need it; resubmitting only the failed `custom_id`s is correct.
- **Assuming batch results can't be matched back to inputs ("keep everything in submission order")** — a misconception; `custom_id` is designed exactly for this correlation, independent of ordering.
- **Running the full-volume batch first to "see what happens"** — skips sample-based prompt refinement, so systematic prompt issues are discovered only after a slow, costly batch run instead of a fast synchronous iteration loop.
