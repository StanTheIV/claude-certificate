# Structured Output with tool_use and JSON Schemas

## tool_use eliminates syntax errors, not semantic ones

Asking Claude to "respond with JSON matching this format" in plain text can still produce invalid JSON: a missing brace, a trailing comma, a field with the wrong type. The most reliable way to guarantee syntactically valid, schema-shaped output is to define an extraction **tool** whose input parameters are a JSON schema, and read the structured data back out of the model's `tool_use` response instead of parsing free text.

```json
{
  "name": "extract_invoice",
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor": {"type": "string"},
      "total": {"type": "number"},
      "line_items": {"type": "array", "items": {"type": "object"}}
    },
    "required": ["vendor", "total"]
  }
}
```

When the model calls this tool, its arguments are guaranteed to be syntactically valid JSON matching the declared types and required fields — no missing braces, no field with the wrong data type. This eliminates an entire class of parsing failures.

What it does **not** guarantee is that the *values* are correct: a `total` field can still be syntactically a valid number while being the wrong number, or a value can land in the wrong field even though the JSON is well-formed. Structural correctness (schema) and semantic correctness (facts) are two separate problems, and tool_use only solves the first one.

> **Key idea:** `tool_use` + JSON schema removes syntax errors entirely. It does nothing to catch a total that doesn't sum, a date in the wrong field, or a fabricated value — those need validation, described in the next lesson.

> **Note (current docs):** Current docs also offer an optional `strict: true` flag on a tool definition, which further guarantees required fields, enum values, and (with `additionalProperties: false`) no extra fields. It still does not guarantee semantic correctness — a strictly valid `total` field can still hold the wrong number.

## Controlling tool selection with tool_choice

`tool_choice` controls whether — and which — tool the model must call:

| Value | Behavior | When to use |
|---|---|---|
| `{"type": "auto"}` | Model may call a tool or just respond in text | Default; fine when structured output isn't mandatory every time |
| `{"type": "any"}` | Model must call **some** tool, but picks which one | Multiple extraction schemas exist and the document type is unknown, but you still need guaranteed structured output |
| `{"type": "tool", "name": "extract_metadata"}` | Model must call **this specific** tool | You need a guaranteed first step, e.g. metadata extraction must run before an enrichment step can use it |

With `"auto"`, nothing stops the model from answering in plain text instead of calling a tool — acceptable for a chat assistant that only sometimes needs structured output, but a poor choice when your downstream code always expects a `tool_use` block. With `"any"`, you give up control over *which* tool runs but guarantee that *some* structured call happens, which fits a pipeline where several extraction schemas exist (invoice, receipt, contract) and you don't know in advance which applies. Forcing a named tool is for cases where the workflow has a required order — extracting metadata before enrichment can run — and you cannot allow the model to skip or reorder that step.

> **Exam trap:** Using `"auto"` when the downstream code always expects structured output is a common setup for a bug: the model occasionally answers conversationally instead of calling the tool, and the parsing code has nothing to parse.

## Nullable fields prevent fabrication

If a schema field is marked `required` but the source document simply doesn't contain that information, the model faces a bad choice: return something anyway (fabricate a value) or fail the tool call. Marking a field **optional and nullable** gives it a third, honest option:

```json
"contract_end_date": {
  "type": ["string", "null"],
  "description": "ISO 8601 date, or null if the document does not state an end date"
}
```

Only mark a field `required` when the information is essentially always present in your source documents. For anything that might legitimately be missing, use a nullable type and describe in the field's description exactly when `null` is the correct answer. This directly targets a known failure mode: a model asked to always produce a value for a required field will sometimes invent a plausible-looking one rather than admit the information isn't there.

## "unclear" and "other" + detail for extensible categories

Enum fields force the model to choose from a fixed set of categories, which is good for downstream code but bad when the real world produces a case that doesn't fit any listed value. Two patterns handle this:

```json
"category": {
  "type": "string",
  "enum": ["bug", "feature", "docs", "unclear", "other"]
},
"category_detail": {
  "type": ["string", "null"],
  "description": "Required detail when category is 'other' or 'unclear'"
}
```

- **`"unclear"`** — for cases where the model genuinely cannot determine the right category with confidence. An honest "unclear" beats a guessed category that later needs to be manually corrected.
- **`"other"` + a detail string** — for cases that clearly don't fit any predefined category, but do have a real, describable value. Without this pattern, data outside your predefined list is silently lost or forced into the nearest wrong bucket.

Both patterns keep the enum closed (so downstream code can still switch on a small fixed set of values) while preserving information that a plain enum would otherwise discard.

## Format normalization rules alongside the schema

A strict schema constrains structure and types, but it doesn't tell the model *how* to normalize values that arrive in inconsistent formats across source documents — "5 bucks", "$5.00", and "five dollars" can all be syntactically valid strings in a `price` field while being inconsistent for downstream comparison. Add explicit normalization rules in the prompt text alongside the schema:

```
Normalization rules:
- Dates: always ISO 8601 (YYYY-MM-DD); resolve relative dates ("yesterday") to absolute ones
- Currency: numeric amount + currency code; "five bucks" -> {"amount": 5, "currency": "USD"}
- Percentages: decimal fraction; "half" -> 0.5
```

This is a semantic-error fix, not a syntax fix: the schema alone would happily accept `"amount": "five"` as a string if the field type allowed it, or accept inconsistent date strings as long as they're valid JSON strings. Pairing normalization instructions with the strict schema addresses the gap between "valid JSON" and "consistently usable data."

## Exam lens: why the distractors lose

- **Free-text JSON in the prompt instead of tool_use** — asking the model to "output JSON" in plain text can still produce malformed JSON; `tool_use` with a schema structurally guarantees valid, schema-shaped output.
- **Assuming a valid schema means correct data** — schema validation catches missing fields and wrong types, not a total that doesn't sum or a value copied into the wrong field. That gap needs validation and retry (next lesson), not a stricter schema.
- **`tool_choice: "auto"` for a pipeline that always needs structured output** — leaves open the possibility the model answers in text instead of calling a tool; `"any"` or a forced tool name guarantees a tool call happens.
- **Required fields for information that's sometimes absent from the source** — pushes the model toward fabricating a value to satisfy the schema; nullable optional fields let it honestly report "not present."
- **A plain enum with no "other"/"unclear" option** — forces every real-world value into the nearest wrong category or drops it; the "other" + detail and "unclear" patterns preserve information a closed enum would otherwise lose.
- **Relying on the schema alone for format consistency** — a schema enforces types, not normalization; inconsistent currency/date formats need explicit normalization rules in the prompt in addition to the schema.
