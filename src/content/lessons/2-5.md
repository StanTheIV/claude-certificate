# Selecting Built-in Tools Effectively

## The decision table: six tools, six jobs

Claude Code's built-in tools look interchangeable at a glance — several of them can "find things" or "change things" — but each one is the *right* answer for a narrow slice of tasks, and picking wrong costs time or produces incomplete results. Start from what you're actually trying to do:

| You want to... | Use | Not |
|---|---|---|
| Find files by name or path pattern (`**/*.test.tsx`) | **Glob** | Grep (that searches contents, not names) |
| Search file *contents* for a pattern (a function name, an error string, an import) | **Grep** | Glob (that doesn't look inside files) |
| Load a whole file to read and understand it | **Read** | Grep (which returns matching lines, not context) |
| Create a brand-new file, or replace a file's entire contents | **Write** | Edit (Edit assumes the file already has the text you're targeting) |
| Make a small, targeted change to one part of an existing file | **Edit** | Write (rewriting the whole file risks losing unrelated content and is harder to review) |
| Run a shell command — tests, a build, `git log`, installing a package | **Bash** | Any of the above — none of them execute processes |

The common confusions worth memorizing: Grep vs. Glob is content vs. path, not "which one is more powerful" — they answer different questions. Edit vs. Write is targeted vs. wholesale — Edit is preferred when it applies because it's a smaller, safer, more reviewable change. Bash is the only one of the six that runs anything; the other five only read or write files.

> **Key idea:** Each tool answers one specific question — "where is this text?" (Grep), "what files match this name pattern?" (Glob), "what's the whole content?" (Read), "run this command" (Bash). Picking the tool means first stating the question precisely.

## Grep vs Glob: content search vs path matching

These two are the pair most often swapped by mistake, because both "search" for something.

- **Grep searches inside file contents.** Use it to find all callers of a function, locate every place an error message appears, find an import statement, or search for a specific string or regex pattern across a codebase. The result is a set of matching lines (with file and line number), not a list of filenames.
- **Glob matches file *paths* against a pattern.** Use it to find "every test file" (`**/*.test.tsx`), "every TypeScript file under `src/components`" (`src/components/**/*.ts`), or "the config file at the project root." Glob never looks at what's *inside* a file — it only matches names and directory structure.

A useful check: if the request is phrased as "find all files that..." followed by a naming or extension pattern, that's Glob. If it's phrased as "find everywhere that..." followed by a piece of code, text, or a symbol name, that's Grep. Asking Glob to "find the function `processRefund`" will not work — no filename matches that pattern — Grep is what searches inside files for it.

## Read/Write vs Edit: full-file operations vs targeted change

**Read** loads a file's full content so you (or the model) can understand it in context — necessary before making any non-trivial change, and the natural tool once Grep or Glob has pointed you at the right file.

**Write** creates a new file, or replaces a file's entire content. It's the right tool when there's no existing content to preserve (a brand-new file) or when the change is so extensive that rewriting the whole file is clearer than describing a series of edits.

**Edit** makes a targeted, precise modification: it finds a unique piece of existing text and replaces just that piece, leaving the rest of the file untouched. This is the preferred tool for small, surgical changes — fixing one function, updating one config value, correcting one line — because it changes only what needs to change and is easy to review against the original.

The trade-off: Edit is safer and more precise *when it applies*, but it depends entirely on the target text being unambiguous.

## Edit's unique-match rule, and the Read+Write fallback

Edit works by matching a specific snippet of text and replacing it. That snippet must be **unique** within the file — if the same text appears more than once, Edit cannot tell which occurrence you meant, and the call fails rather than guessing.

This happens more often than it sounds: a short snippet like `return null;` or a repeated boilerplate block can easily appear several times in the same file. When Edit fails for this reason, the fallback is:

1. **Read** the full file content.
2. Modify the content (expand the target snippet with more surrounding context, or compute the new content programmatically).
3. **Write** the updated version back, replacing the whole file.

This isn't a workaround to avoid — it's the documented, correct response to a non-unique match. Read + Write guarantees the right occurrence changes, at the cost of handling the whole file's content instead of a small diff. The alternative — retrying Edit with a slightly different snippet and hoping it becomes unique — is fragile and can still land on the wrong occurrence if you're not careful about what makes the snippet unique.

> **Exam trap:** When Edit fails on a non-unique match, guessing at a longer anchor string and retrying blindly might work, but it isn't the reliable answer — you can still pick text that matches multiple spots you didn't expect, or under-shoot and get another failure. Read + Write is the deterministic fallback: you see the whole file before deciding exactly what changes.

## When Bash is the right call — and when it isn't

Bash is the only built-in tool that executes something rather than reading or writing file content directly. It's the right choice for running tests (`npm test`), builds, linters, package installs, and git operations (`git log`, `git diff`, `git blame`) — anything where the actual output depends on running a real process, not on the static content of a file.

It is tempting to reach for Bash for tasks another tool already does better, but that's usually a step backward:

- Using `grep`/`find` via Bash instead of the Grep/Glob tools loses the integration these tools have with the surrounding environment (result formatting, path handling) and reintroduces shell-escaping and cross-platform quoting concerns for no benefit.
- Using `cat` via Bash instead of Read, or shell redirection instead of Write/Edit, does the same job with less structure and no unique-match safety net.
- Conversely, trying to run a test suite or check `git blame` with Read/Grep/Glob doesn't work at all — none of them execute anything; only Bash spawns a process.

The dividing line: if the task is "find or view existing file content," prefer Grep, Glob, Read, Write, or Edit — they're purpose-built and safer. If the task is "run something and see what happens" — tests, builds, version control history, installing a dependency — that's what Bash is for, and no other built-in tool can do it.

## Incremental investigation and tracing through wrapper modules

Reading every file in a codebase upfront wastes context and time. The efficient pattern builds understanding incrementally:

1. **Grep** to find entry points — a function definition, an export, a specific error message.
2. **Read** the files that match, to understand what they actually do.
3. **Grep** again for usages — imports, calls to what you just read.
4. **Read** the consumer files that come back.
5. Repeat until the picture is complete, rather than reading the whole tree first and hoping the relevant part stands out.

A specific variant of this shows up with wrapper or re-export modules: a function might be defined in one file, then re-exported under a different name from an index or barrel file, and called under yet another alias somewhere else. Grepping for the original function name alone can miss callers that only ever see the wrapper's name. The reliable approach is to first identify *all* the exported names a wrapper module produces (including re-exports and aliases), then Grep separately for each of those names across the codebase. Skipping this step is exactly how "I found all the callers" turns out to have missed a whole call site that only used the wrapper's alias.

## Exam lens: why the distractors lose

- **Using Grep to "find all test files"** — Grep searches file *contents*; it has nothing to match against a bare naming request unless the pattern happens to also appear as text inside files. Glob is built for path/name matching and is both correct and faster for this.
- **Reading every file in the directory before making a change** — works eventually, but burns context budget on files that turn out to be irrelevant. Grep-first, then targeted Read, gets to the same understanding with a fraction of the tokens.
- **Retrying Edit with a slightly longer snippet after a non-unique match, without reading the file first** — can accidentally land on the wrong occurrence again, or still fail, because you're guessing at uniqueness blind. Read + Write removes the guesswork by showing you the whole file before you decide what to change.
- **Rewriting a whole file with Write for a one-line fix** — works, but is a larger, harder-to-review change than necessary, and risks silently dropping unrelated content if the "full new content" wasn't reconstructed perfectly. Edit is the tighter, safer tool when the target text is unique.
- **Shelling out through Bash for a plain content search or file listing** (`bash grep ...`, `bash find ...`) — technically works, but it's a shell-quoting and cross-platform liability for a job Grep/Glob already do more safely. Save Bash for what only Bash can do: running processes like tests, builds, and git commands.
- **Grepping only for a function's original definition name** when tracing usage through a wrapper or barrel module — silently misses call sites that only reference a re-exported alias. Enumerate every exported name first, then search for each one.
