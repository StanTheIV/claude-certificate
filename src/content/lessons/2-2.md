# Structured Error Responses for MCP Tools

## The isError flag: how MCP tools report failure

When an MCP tool call fails, the response sets `isError: true`. This is the signal the agent uses to know the call did not succeed — without it, the agent has no reliable way to distinguish a real result from a failure dressed up as one.

Setting the flag is only half the job. What matters just as much is *what* goes in the response content when `isError` is true. A tool can technically comply with the protocol and still be useless to the agent:

```json
{ "isError": true, "content": "Operation failed" }
```

This tells the agent a `process_refund` call did not work, but nothing about *why* — was the order ID invalid? Was the refund amount over a policy limit? Was the payment service down? The agent cannot recover intelligently because it wasn't given anything to reason about. The rest of this lesson is about replacing that string with metadata the agent can act on.

> **Key idea:** `isError: true` answers "did it work?" Everything else in the response should answer "what should I do now?"

## Four error categories, one decision: is this retryable?

Not all failures deserve the same response. MCP tool errors generally fall into four categories:

| Category | Example | Retryable? |
|---|---|---|
| **Transient** | Timeout, service unavailable, network failure | Yes — retry, often with backoff |
| **Validation** | Invalid input format, missing required field | No — fix the input, then retry |
| **Business** | Policy violation, refund exceeds threshold | No — explain to the user, offer an alternative |
| **Permission** | Access denied | No — escalate, don't retry |

The category is what turns a failure into a decision. A transient error means "try again, maybe with a different approach." A validation error means "the request itself was malformed — retrying the identical call will fail again." A business error means the call *worked* — the system correctly rejected it — and the right response is to communicate the policy, not retry. A permission error means the agent's access is the problem, and no amount of retrying fixes that; it needs a human.

## Structured metadata vs the generic "Operation failed"

A well-designed error response carries this categorization explicitly, so the agent doesn't have to guess from the message text:

```json
{
  "isError": true,
  "content": {
    "errorCategory": "transient",
    "isRetryable": true,
    "message": "The service is temporarily unavailable. Timeout while calling the orders API.",
    "attempted_query": "order_id=12345",
    "partial_results": null
  }
}
```

Three fields do most of the work: `errorCategory` (transient / validation / business / permission), `isRetryable` (a boolean the agent can branch on directly, without parsing prose), and a human-readable `message` the agent can relay if it needs to explain the failure to a user. For a business-rule violation specifically, pair `"isRetryable": false` with a customer-friendly explanation — "Refunds over $500 require manager approval" — so the agent can communicate the *reason*, not just report that something failed.

> **Exam trap:** A uniform "Operation failed" string is tempting because it's simple to implement everywhere. But uniform responses force the agent to either blindly retry (wasting calls on non-retryable failures) or blindly give up (on failures that would have succeeded on retry). Structured metadata isn't extra polish — it's what makes automated recovery possible at all.

## Recover locally, escalate what you can't fix

Not every error needs to travel all the way to a coordinator or a user. For transient failures, a subagent should attempt local recovery first — typically one or two retries, not an unbounded loop — before giving up.

What gets propagated is what *couldn't* be resolved locally, and it should include more than a failure notice: the failure type, what was attempted, any partial results already gathered, and — where possible — an alternative approach. This is the same shape as the structured error itself, just aggregated one level up:

```json
{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "AI impact on music industry 2024",
  "partial_results": [{"title": "AI Music Generation Report", "relevance": 0.8}],
  "alternative_approaches": ["Try a narrower query: 'AI music composition tools'"]
}
```

Retrying forever inside a subagent wastes latency and resources on a failure that local recovery already couldn't fix. Aborting the entire workflow on one subagent's failure discards partial results that were still useful. The middle path — bounded local retries, then propagate with context — is what lets a coordinator make an informed decision instead of an all-or-nothing one.

## Empty result is not the same as a failed call

One of the easiest mistakes to make is collapsing two very different outcomes into the same shape: a search that ran successfully and found nothing, and a search that could not run at all.

- **Valid empty result:** the query executed correctly against the system; there are genuinely no matching orders, customers, or documents. This is `isError: false` (or absent) with an empty result set.
- **Access failure:** the query could not be answered — a timeout, a permission error, a malformed query. This must be `isError: true` with a category, even though from a distance it might "look like" nothing came back.

If a tool silently returns an empty array marked as success for both cases, the agent (and downstream synthesis) will treat "we don't have data because access failed" as "we checked, and there's nothing there" — a much stronger and often wrong claim. This distinction is what lets a coordinator decide between "report no matches" and "retry or escalate the access problem."

## Exam lens: why the distractors lose

- **Generic status strings ("search unavailable", "Operation failed")** — hide the information the agent needs to choose retry vs. escalate vs. explain. They look like they satisfy "report the error," but they remove the agent's ability to act on it.
- **Marking a failure as a successful empty result** — silently suppresses the error instead of surfacing it. It avoids an awkward status code in the short term but produces confidently wrong downstream conclusions ("no matches found" when the real story is "the lookup failed").
- **Unbounded retries inside a subagent** — feels safe ("just keep trying until it works") but burns latency and resources on failures that bounded local recovery already showed aren't resolving. The deciding principle: retry locally a small, fixed number of times, then propagate with context — don't retry forever and don't propagate immediately without trying at all.
- **Aborting the entire workflow on a single tool failure** — overreacts. One subagent's timeout doesn't mean the whole task is unrecoverable; propagating structured context (including partial results) lets the coordinator continue with a noted gap instead of losing everything.
- **Treating "permission denied" as retryable** — retrying with the same credentials will not change the outcome. Permission errors need escalation, not a backoff loop; conflating them with transient errors wastes cycles on a failure that only a human (or a config change) can fix.
