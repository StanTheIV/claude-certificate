# Manage Context Effectively in Large Codebase Exploration

## Recognizing context degradation

In a long codebase-exploration session, context does not fail all at once — it degrades gradually. A telltale sign: the model starts giving inconsistent answers across turns, and instead of referencing the specific classes and files it found earlier in the session, it starts describing "typical patterns" in generic terms ("this usually follows a repository pattern" instead of "the `OrderRepository` class in `src/db/orders.ts`").

This happens because early, specific findings get pushed deep into a context window that keeps growing with every file read, every grep result, every tool call. The specific facts are technically still "in there," but they compete with a large volume of less relevant content, and the model's answers drift toward generic plausible-sounding statements instead of grounded, specific ones.

> **Key idea:** Treat "the model starts talking in generalities about code it already found specifically" as a concrete warning sign that context needs active management, not just a quirk to shrug off.

## Delegating verbose exploration to subagents

A large share of context in codebase exploration is consumed by *process*, not *conclusions*: reading fifteen files to figure out one dependency chain produces a lot of file content that the main agent doesn't need to keep around once the answer is known.

The fix is to spawn subagents for specific, scoped investigative questions — "find all test files," "trace refund flow dependencies" — and let each subagent do the verbose reading and searching in its own isolated context. The subagent returns a concise answer; the main agent's context absorbs one summary line instead of fifteen files' worth of content:

```
Main agent: "Investigate dependencies of the payments module"
  -> Subagent (Explore): reads 15 files, traces imports
  -> Returns: "Payments depends on AuthService, OrderModel, and the external PaymentGateway API"

Main agent: keeps one line in context instead of 15 files
```

The main agent's job throughout is high-level coordination: deciding what to investigate next and synthesizing subagent findings, not doing the verbose reading itself.

## Scratchpad files to survive context boundaries

For findings that need to persist beyond what fits comfortably in the model's working context — across a long session, across a `/compact`, or across a fresh session entirely — write them to a scratchpad file:

```
# investigation-scratchpad.md
## Key findings
- PaymentProcessor in src/payments/processor.ts inherits from BaseProcessor
- refund() is called from 3 places: OrderController, AdminPanel, CronJob
- External PaymentGateway API has a rate limit of 100 req/min
- Migration #47 added refund_reason (NOT NULL) — 2024-12-01
```

When context degrades, or when a new session picks up the investigation, the agent can read this file and get back the specific facts it already established, instead of re-running the same discovery work from scratch (which costs both time and tokens, and risks arriving at a slightly different, inconsistent answer the second time).

## Phase summaries before the next round of subagents

For multi-phase investigations, don't let each new phase's subagents start from nothing, and don't let them inherit the full raw output of the previous phase either. Instead, summarize the key findings from one exploration phase into a compact form, and inject that summary into the initial context of the subagents for the next phase.

This keeps each phase's subagents grounded in what was already learned, without forcing them to re-read everything the previous phase touched. It is the same principle as the case-facts block from context management in general: carry forward the *distilled facts*, not the *raw process* that produced them.

## Manifests for crash recovery, and /compact for long sessions

For long-running, multi-agent investigations that might be interrupted (a crash, a timeout, a manual pause), design for recovery up front: each agent exports its own state to a known location, and the coordinator writes and reads a manifest summarizing overall progress.

```json
// agent-state/web-search-agent.json
{
  "status": "completed",
  "queries_executed": ["AI music 2024", "AI music composition"],
  "key_findings": [ /* ... */ ],
  "gaps": ["music distribution", "music licensing"]
}
```

```json
// agent-state/manifest.json
{
  "web-search": "completed",
  "doc-analysis": "in_progress",
  "synthesis": "not_started"
}
```

On resume, the coordinator loads the manifest, sees which agents already finished, and injects each agent's exported state back into its prompt instead of starting the whole investigation over.

Separately, for a single long session that has filled up with verbose discovery output (lots of file reads and search results, not yet lost but crowding the window), use `/compact` to reduce context usage by summarizing the conversation so far. This is a different tool for a different situation than the manifest pattern: `/compact` manages one session's accumulated context; manifests manage recovery *across* sessions or after a crash.

## Exam lens: why the distractors lose

- **Trusting the model's fluent, generic-sounding answer vs. treating "typical patterns" language as a warning sign** — a confident-sounding answer about generic patterns is not the same as a grounded answer about the specific code already found; the deciding signal is specificity, not fluency.
- **Having the main agent read all fifteen files itself vs. delegating to a subagent that returns one summary line** — reading everything in the main agent's own context burns the budget that later steps need; isolating verbose reading in a subagent protects it.
- **Re-running discovery from scratch after a context reset vs. consulting a scratchpad file** — re-discovery costs time and risks a second, slightly different (inconsistent) answer; a scratchpad preserves the first grounded answer.
- **Passing a whole previous phase's raw output into the next phase's subagents vs. injecting a distilled summary** — raw carry-over reintroduces the same volume problem one phase later; a summary keeps only what's needed.
- **Restarting an interrupted multi-agent job from zero vs. loading a manifest and injecting exported state** — restarting throws away completed subagents' work; a manifest lets the coordinator resume only what's actually unfinished.
- **Switching to a larger context window instead of using `/compact` or delegation** — a bigger window delays the problem but doesn't address degradation quality (see 5.1's lost-in-the-middle effect); active context management is the fix, not just more room.
