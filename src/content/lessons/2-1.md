# Designing Tool Interfaces

## Why descriptions decide which tool gets called

Claude does not see your code. When it decides whether to call `get_customer` or `lookup_order`, the only information it has is the tool's `name`, its `description`, and its `input_schema`. The description is the **primary mechanism** the model uses to select a tool — not comments in your source file, not variable names, not how the tool is implemented internally.

This means a minimal description is not just unhelpful documentation — it is a missing piece of the decision logic. If `get_customer` is described as "Retrieves customer information" and `lookup_order` as "Retrieves order details," both descriptions are technically true, but neither tells the model when a request like "check my order #12345" should route to `lookup_order` instead of `get_customer`. In production, this kind of gap shows up as a measurable pattern: the wrong tool gets called for a recognizable class of requests, even though both tools work correctly on their own.

> **Key idea:** Treat the tool description as part of your system's decision logic, not as documentation. If two tools could plausibly both match a request, the description is the only thing standing between the model and a wrong call.

## What a strong description includes

A tool description that reliably differentiates a tool from its neighbors needs four kinds of information:

1. **What it does and returns.** Not just the action, but the shape of the result.
2. **Input formats and example values**, so the model knows what a valid call looks like (an email vs. a numeric ID, a date format, an order number pattern).
3. **Edge cases and boundaries** — what the tool does *not* do, and what happens with missing or ambiguous input.
4. **When to use this tool versus similar alternatives.** This is the part minimal descriptions always skip, and it is usually the part that fixes misrouting.

For example, a description for `get_customer` might read: "Finds a customer by email or numeric ID. Returns the customer profile, including name, email, order history, and account status. Use this tool BEFORE `lookup_order` to verify identity. Accepts an email (format: `user@domain.com`) or a numeric `customer_id` — not an order number." That last sentence alone removes most of the ambiguity with `lookup_order`.

## Worked example: from vague to precise

Consider two tools with these original descriptions:

- `analyze_content`: "Analyzes content and returns insights."
- `analyze_document`: "Analyzes a document and returns insights."

A model cannot reliably tell these apart — both descriptions are near-identical, and neither states an input format, a data source, or a boundary. The fix is not to add more adjectives; it is to state, concretely, what each tool consumes and when it applies:

- `analyze_content` → renamed `extract_web_results`: "Fetches a web page by URL and extracts its main text content, title, and publish date. Use for public web pages found via search. Does not handle PDFs or files already in the conversation."
- `analyze_document`: "Analyzes an already-uploaded document (PDF, DOCX) attached to this conversation and extracts structured data points. Use only for documents provided directly by the user, not for URLs."

Once the descriptions name the input type and the boundary, the overlap disappears.

## Renaming and splitting tools to remove overlap

Sometimes better wording is not enough — the tool itself is doing too many unrelated jobs, and no description can cleanly separate "when to use it" because the answer is "it depends what you ask it to do."

Two concrete fixes appear repeatedly in production tool design:

- **Rename to remove a misleading name.** `analyze_content` sounds generic enough to match almost any request. Renaming it to `extract_web_results` immediately narrows what a model expects it to do, before the description is even read.
- **Split a generic tool into purpose-specific tools with distinct contracts.** A generic `analyze_document` tool that "does everything with a document" is hard to describe precisely. Splitting it into `extract_data_points` (pulls structured fields), `summarize_content` (produces a prose summary), and `verify_claim_against_source` (checks one claim against the document text) gives each tool a narrow, describable contract — and gives the model three unambiguous choices instead of one tool it has to guess the intent for.

> **Exam trap:** Adding more few-shot examples to the system prompt "fixes" misrouting on the examples you wrote, but it adds token overhead and does not generalize to new phrasings the way a clear, boundary-stating description does. When the root cause is a minimal or overlapping description, rewriting the description is the lower-effort, higher-leverage first step — not more examples.

## When the system prompt fights the tool description

Tool descriptions do not act alone. The system prompt sets the frame the model reasons within, and keyword-sensitive instructions can quietly override a well-written description. If a system prompt says "Always look up customer information first when a user mentions an issue," a model may call `get_customer` even for a pure order-status question, because the instruction's keyword ("customer") matches more strongly than the tool boundary the description tried to establish.

This is why reviewing tool selection failures should not stop at the tool definitions. Ask: does anything in the system prompt create an association with a keyword that isn't actually the deciding factor? A phrase like "customer issue" is a weak, keyword-driven trigger; a phrase like "verify identity only when the request involves account changes" is a boundary-respecting instruction that works with the tool descriptions instead of against them.

## Exam lens: why the distractors lose

- **Few-shot examples instead of better descriptions** — plausible, and it does reduce errors on the patterns you demonstrate, but it adds ongoing token cost and doesn't fix the root cause (the model still can't generalize to unseen phrasings). Rewriting the description is lower-effort and fixes the actual gap.
- **A routing/classifier layer in front of tool selection** — over-engineered for a "first step." It bypasses the model's language understanding entirely and adds infrastructure to maintain, when the real fix is a text change to two descriptions.
- **Consolidating two tools into one generic tool** — can be the right long-term architecture, but it is more effort than the situation calls for as an immediate fix, and a single overloaded tool still needs a precise input contract or the ambiguity just moves inside the tool.
- **Blaming the wrong layer** — assuming a misrouted call means the model "isn't smart enough," rather than checking whether the description and system prompt actually gave it enough information to decide. The deciding principle: before adding infrastructure or examples, ask whether the tool's own description already contains enough boundary information — most misrouting traces back to text you can edit directly.
- **A programmatic hook that blocks the "wrong" tool** — useful for enforcing a mandatory *sequence* (verify identity before refund), but it solves ordering, not ambiguous *selection* between two tools that could each be a legitimate first call. Don't reach for enforcement machinery when the problem is that the model can't tell two tools apart.
