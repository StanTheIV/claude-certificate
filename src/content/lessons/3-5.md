# Iterative Refinement for Progressive Improvement

## Concrete input/output examples beat prose

When you describe a transformation in prose — "normalize the phone numbers" or "convert these records to the new format" — Claude has to guess at edge cases you didn't spell out, and different runs can interpret the same sentence differently. The fastest fix is usually not a longer, more careful sentence. It's **2-3 concrete input/output examples** showing exactly what a correct transformation looks like:

```
Input:  "(555) 123-4567"        ->  Output: "+15551234567"
Input:  "555.123.4567 ext 89"   ->  Output: "+15551234567" (extension dropped)
Input:  "call me at 5551234567" ->  Output: "+15551234567"
```

A handful of well-chosen examples pins down exactly the behavior a paragraph of prose leaves ambiguous — including edge cases (an extension present, no punctuation) that a general instruction is unlikely to anticipate on its own. This is the same principle as few-shot prompting applied specifically to *iterative* work: when the first attempt at a prose description produces inconsistent results, examples are the fastest correction.

> **Key idea:** when prose produces inconsistent results across runs, add examples before you add more prose.

## Test-driven iteration

For tasks with a clear notion of "correct," write the test suite *before* asking for the implementation:

1. Write tests covering expected behavior, edge cases, and any performance requirements.
2. Ask Claude to implement against those tests.
3. Run the tests. If some fail, share the **specific failures** — not just "it doesn't work" — and let Claude iterate against that concrete feedback.
4. Repeat until the suite passes.

This turns "iteration" from a vague back-and-forth into a converging loop: each round has an objective signal (which tests pass, which fail, and why) instead of relying on you re-describing the problem from memory each time. It also means the requirements were fully specified *before* implementation started, catching ambiguity early rather than after code exists.

> **Exam trap:** iterating by re-explaining the requirement in different words each round, without a fixed test suite to check against, has no stable target — you can't tell if you're converging or just changing.

## The interview pattern

Before implementing something in an unfamiliar domain, have Claude *ask questions* rather than immediately proposing a solution. For example, before implementing caching for an API:

```
Claude: "Before implementing caching for the API, a few questions:
1. Which cache invalidation strategy do you prefer — TTL or event-based?
2. Is stale data acceptable when the cache is unavailable?
3. Should caching be per-user or global?
4. What is the expected data volume to cache?"
```

This surfaces considerations the developer may not have thought to specify up front — cache invalidation strategy, failure-mode behavior, scope — *before* a design commits to answers for all of them implicitly. It's most valuable in unfamiliar domains (fintech, healthcare, legal systems) and for problems with non-obvious implications, where the "obvious" first implementation often has an unstated assumption baked in.

> **Key idea:** the interview pattern trades a short delay up front for avoiding a design built on an assumption nobody actually agreed to.

## Single message vs sequential fixes

When you have multiple issues to address, how you deliver them matters:

- **Interacting issues** — fixes that depend on or conflict with each other (e.g. a validation rule and a related error-message format that must stay consistent) — should go in **one detailed message**. If you fix them one at a time, an earlier fix can be partially undone or contradicted by a later one that doesn't account for it.
- **Independent issues** — unrelated bugs with no shared logic — are fine to fix **sequentially**, one iteration at a time. This keeps each round focused and easy to verify in isolation.

Worked example: null values causing a migration script to crash. Give a specific test case with the exact input (a record with a null field) and the exact expected output (how the script should handle it), rather than a generic "handle nulls better" — this is the same "concrete examples over prose" principle applied to fixing an edge case, not just building a new feature.

> **Exam trap:** batching *unrelated* fixes into one giant message doesn't help — it just makes it harder to verify which change addressed which bug. Batching only pays off for fixes that genuinely interact.

## Exam lens: why the distractors lose

- **Rewriting the prose instruction to be longer and more emphatic** loses to adding 2-3 concrete input/output examples — when the problem is ambiguity, more words describing the same ambiguous rule don't resolve it; concrete examples do.
- **Iterating by re-describing the bug from memory each round, with no fixed test suite** loses to test-driven iteration — there's no stable signal for whether you're converging, and earlier feedback can get lost between rounds.
- **Jumping straight to an implementation in an unfamiliar domain** loses to the interview pattern when the problem has non-obvious implications (cache invalidation, failure modes) — the first implementation is likely to bake in an assumption nobody actually agreed to.
- **Fixing two interacting issues one at a time, sequentially** loses to addressing them together in one message — an isolated fix to one can be undone or contradicted by the next fix that doesn't know about it.
- **Batching unrelated, independent bugs into one large combined fix request** loses to sequential iteration — it makes it harder to verify each fix independently and increases the chance an unrelated change gets tangled with another.
- **"Give a generic instruction to handle edge cases better"** loses to providing a specific test case with concrete input and expected output — a generic instruction doesn't specify what "handled" means for the case that's actually failing.
