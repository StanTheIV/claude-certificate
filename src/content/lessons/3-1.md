# Configuring CLAUDE.md: Hierarchy, Scoping, and Modular Organization

## The three-level CLAUDE.md hierarchy

`CLAUDE.md` is how you give Claude Code persistent instructions instead of retyping them every session. There are three scopes:

1. **User-level** — `~/.claude/CLAUDE.md`. Applies only to that one developer, on every project they open. Good for personal working style ("I prefer verbose commit messages").
2. **Project-level** — `.claude/CLAUDE.md` or a root `CLAUDE.md`. Applies to every contributor on the project. This is where coding standards, testing conventions, and architectural decisions belong.
3. **Directory-level** — a `CLAUDE.md` placed inside a subdirectory. Applies only when Claude is working with files in that directory, for conventions specific to one part of the codebase (e.g. `src/payments/CLAUDE.md` for payment-module rules).

All three can be present at once; Claude loads the ones that apply to where it's working. The scopes exist so you can put an instruction exactly where it's relevant: personal preferences don't belong in a file the whole team reads, and team standards don't belong in a file only you can see.

> **Key idea:** pick the *narrowest* scope that still reaches everyone who needs the instruction. Team-wide testing rules go in project-level; your own shortcut key habits go in user-level.

## Diagnosing hierarchy issues

The most common real-world failure is scope confusion. A new team member clones the repository, but Claude doesn't seem to know the project's conventions — even though a senior engineer swears "it's all in CLAUDE.md."

The likely cause: the instructions were written into `~/.claude/CLAUDE.md` (user-level) instead of `.claude/CLAUDE.md` (project-level). **User-level settings are not shared with teammates via version control** — they live in the individual developer's home directory and never get committed. The senior engineer's Claude behaves correctly because their personal file has the instructions; everyone else's Claude has never seen them.

The fix is always to move (or duplicate) the instruction to the project-level file, which is checked into the repository and therefore reaches every clone. When you're troubleshooting "Claude doesn't follow our conventions," the first question is always *which file, at which scope, is this instruction actually in?*

> **Exam trap:** a question may offer "tell the developer to run `/memory` and manually copy their personal instructions to every teammate" — this treats a scoping problem as a communication problem. The real fix is moving the instruction to the scope that's already shared by version control, not adding a manual workaround.

## Modular CLAUDE.md with `@` imports

A single project-level `CLAUDE.md` can grow unwieldy if it tries to hold every convention for every package. The `@` import syntax keeps it modular by referencing external files:

```markdown
# Project CLAUDE.md
Coding standards are in @./standards/coding-style.md
Testing requirements are in @./standards/testing-requirements.md
See @README.md for project overview and @package.json for scripts.
```

Rules for `@` imports:
- Put `@` immediately before the path, with no space.
- Both relative and absolute paths work; relative paths resolve relative to the file that contains the import, not your working directory.
- Imports can nest — an imported file can itself import another file — up to about 5 levels deep.

This lets a maintainer with domain knowledge of one package selectively include only the standards files relevant to that package's `CLAUDE.md`, instead of forcing everyone to read one giant file cover to cover.

> **Note (current docs):** current Claude Code documentation caps recursive imports at 4 hops rather than 5. Either way, the practical lesson is the same: keep import chains shallow.

## `.claude/rules/` instead of a monolithic file

When a project's `CLAUDE.md` keeps growing because it covers many unrelated topics, split it into `.claude/rules/`: a directory of small, topic-focused Markdown files instead of one large document.

```
.claude/rules/
  testing.md          -- how to write and run tests
  api-conventions.md  -- REST endpoint conventions
  deployment.md       -- release and deploy steps
```

Each file covers one topic, so it's easy for a maintainer to find and update the relevant section without scrolling through hundreds of lines of unrelated content. This is purely an organizational upgrade over a monolithic `CLAUDE.md` — files here with no special scoping still load the same way a project `CLAUDE.md` does. (Task 3.3 covers the more advanced version, where each rule file only loads for matching file paths.)

> **Key idea:** `.claude/rules/` is to `CLAUDE.md` what splitting a 2,000-line module into focused files is to code — same content, more maintainable structure.

## Using `/memory` to verify what's loaded

Instructions that live in a file only help if Claude actually loaded that file. `/memory` is the built-in command for checking this: it opens the memory configuration for editing and lets you confirm which `CLAUDE.md` files (user, project, directory) are active in the current session.

This matters most when behavior is inconsistent across sessions or across teammates — the kind of "it works for me but not for them" bug the previous section described. Instead of guessing why Claude isn't following a rule, run `/memory` and check whether the file you edited is actually one of the files being loaded, and at which scope.

`/memory` is also useful after reorganizing configuration (for example, after moving instructions from a monolithic `CLAUDE.md` into `.claude/rules/`) — it lets you verify the split didn't silently drop content that nothing now loads.

> **Key idea:** when behavior seems wrong, don't assume the instruction is bad — first verify with `/memory` that the instruction was loaded at all.

## Exam lens: why the distractors lose

- **"Tell the team to update their personal CLAUDE.md"** loses to *"move the instruction to project-level"* — a scoping problem needs a scope fix, not a per-person workaround that has to be repeated for every new hire.
- **"Put everything in one big root CLAUDE.md for simplicity"** loses to *modular `@` imports or `.claude/rules/`* once the file covers multiple unrelated domains — a monolithic file is harder to maintain and wastes context loading sections nobody needs for the current task.
- **"Assume the instruction is being ignored and rewrite it more forcefully"** loses to *"run `/memory` first"* — diagnose whether the file is loaded before assuming the wording is the problem.
- **A `.claude/config.json` with a `commands` or `memory` array** is a tempting-sounding distractor — no such file exists in Claude Code. Configuration lives in `CLAUDE.md`, `.claude/rules/`, and the directories covered in the next lesson.
- **Directory-level CLAUDE.md for conventions that span the whole codebase** (e.g. one rule that should apply to every test file, wherever it lives) loses to path-scoped `.claude/rules/` — directory-level files are bound to one directory, so they can't reach files scattered across many folders. That's the subject of task 3.3.
