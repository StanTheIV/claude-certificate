# Wire formats: the agent loop in JSON

## One loop turn, end to end

The Repeat unit doesn't teach anything new. It regroups what you learned so you see it the way the exam mixes it. Start with the most-tested mechanism of all, the agentic loop, written as the actual messages that go over the wire.

**1. Request.** Your code sends the full history, the tools and a `tool_choice`:

```json
{
  "model": "claude-...",
  "max_tokens": 1024,
  "system": "You are a customer support agent...",
  "tools": [{ "name": "get_customer", "description": "...", "input_schema": { "...": "..." } }],
  "tool_choice": { "type": "auto" },
  "messages": [{ "role": "user", "content": "I want a refund for order 67890" }]
}
```

**2. Response.** Claude asks for a tool. Look at `stop_reason` and the `tool_use` block:

```json
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "tool_use", "id": "toolu_01...", "name": "get_customer", "input": { "email": "..." } }
  ]
}
```

**3. Next request.** Append the assistant turn, then a **`user`** turn that holds the result:

```json
{ "role": "user", "content": [
  { "type": "tool_result", "tool_use_id": "toolu_01...", "content": "{\"customer_id\": \"CUST-12345\"}" }
] }
```

Three details the exam likes to twist:
- There is **no `"tool"` role**. Tool results travel inside a `user` message as a `tool_result` block, linked by `tool_use_id`.
- The API is **stateless**. You resend the whole `messages` array every call. There is no `session_id` parameter and no server-side memory.
- Your code runs the tool. Claude only *requests* it.

> **Key idea:** loop = call API → if `stop_reason` is `"tool_use"`, run the tool and append the `tool_result` → call again → stop on `"end_turn"`.

## What counts as "done"

The exam guide names only two `stop_reason` values, `"tool_use"` and `"end_turn"`, and those two drive the loop. The API has more; the study guide lists two others worth knowing:

| `stop_reason` | Meaning | Your code does |
|---|---|---|
| `"tool_use"` | Claude wants a tool | Run it, append `tool_result`, continue |
| `"end_turn"` | Claude is finished | Exit the loop, show the result |
| `"max_tokens"` | Output hit the token limit | The answer is **cut off**, not complete. Don't treat it as done |
| `"stop_sequence"` | A stop sequence you set was hit | Application-specific |

> **Note (current docs):** the API now also returns `pause_turn` (send the response back to continue), `refusal` and `model_context_window_exceeded`. The exam's loop logic doesn't change: continue on `tool_use`, finish on `end_turn`.

Signals that *look* like "done" but are not reliable:

| Tempting signal | Why it fails |
|---|---|
| The response contains text | Claude often writes text **and** a `tool_use` block in the same turn |
| Text contains "Task complete" / "Done" | Parsing natural language has no contract; wording varies |
| Stop after N iterations | Stops good runs early and bad runs late. A cap is at most a safety net, never the main stop signal |

One more trap: a script that calls tools in a **fixed, hard-coded order** is not an agentic loop, even if it loops. In an agentic loop, Claude picks the next action.

> **Exam trap:** every weak signal "works in testing". The question is which signal has a documented contract. Only `stop_reason` does.

## Agent SDK configuration to recognise on sight

**Coordinator and subagents.** The coordinator spawns subagents through the **`Task`** tool. If `"Task"` is not in its `allowedTools`, it cannot spawn anything, whatever the prompt says.

```python
coordinator = AgentDefinition(
    name="research_coordinator",
    allowed_tools=["Task"],            # no "Task" = no subagents
)
web_search = AgentDefinition(
    name="web_search",
    description="Searches the web for sources on a given subtopic",
    system_prompt="You are a research assistant...",
    allowed_tools=["web_search"],      # least privilege: only its own tools
)
```

> **Note (current docs):** this is study-guide notation. In the current SDK, `AgentDefinition` uses `prompt` / `tools`, the agent's name is its key in the `agents` dict (no `name` field), and `allowedTools` is a `query()` option. The spawning tool was renamed from `Task` to `Agent` (Claude Code v2.1.63); `Task` still works as an alias. The exam uses `Task`.

Three facts that come as a set:
1. **Isolated context.** A subagent doesn't inherit the coordinator's conversation. The `Task` prompt is its *only* input about the task, so findings, documents and output format must be written into it.
2. **Parallel = one response, many `Task` calls.** One `Task` per turn is sequential and slow.
3. **Hub and spoke.** Subagents never talk to each other; everything goes through the coordinator.

> **Note (current docs):** Claude Code now also has forked subagents that inherit the parent conversation, nested subagents, and `SendMessage` between named agents. For the exam, answer with the strict hub-and-spoke, isolated-context model.

**Hooks** are code that runs at a fixed point, every time:

| Hook | Fires | Canonical use |
|---|---|---|
| `PreToolUse` | *Before* a tool call runs | Block `process_refund` over $500 and redirect to escalation; block refunds until `get_customer` returned a verified ID |
| `PostToolUse` | *After* the tool ran, before Claude sees the result | Normalise dates/status codes; trim a 40-field order record down to the ~5 fields that matter |

## Sessions: resume, fork or start fresh

Three ways to continue earlier work. The deciding question is always: **are the earlier tool results still true?**

| Option | What it does | Choose it when |
|---|---|---|
| `claude --resume <session-name>` | Continues a named session with all its context | Earlier findings are still valid. If a few files changed, **tell the agent which ones** so it re-checks just those |
| `fork_session` | Branches a new, independent session from a shared baseline | You want to try two approaches (e.g. Redux vs Context API) from the same analysis without redoing it |
| New session + structured summary | Starts clean, you pass in the key findings | Much of the earlier tool output is stale; resuming would bring back facts that are now false |

Quick sanity rules:
- A fork doesn't change the original session. Both share context only up to the fork point.
- A named session can be resumed more than once. There is no `--refresh` flag and resume does not check file state for you.
- "Always resume to keep maximum context" is wrong when the context is stale. More context is not better if part of it is false.

> **Key idea:** resume = same path, still valid. Fork = same start, different paths. Fresh = old path is stale.
