# Look-alike pairs: pick the right one of two

## Claude Code configuration pairs

Many questions come down to two mechanisms that both seem to fit. For each pair: when to choose which, and the word in the stem that decides.

| Pair | Choose the first when… | Choose the second when… | Deciding word |
|---|---|---|---|
| **CLAUDE.md** vs **skill** | Universal standards that should always be loaded | A task-specific workflow invoked on demand | "every session" vs "when I run the release" |
| **Slash command** vs **skill** | A simple, fixed prompt you trigger by name | You need isolation (`context: fork`), tool limits (`allowed-tools`, e.g. file writes only) or an argument prompt (`argument-hint`) | "verbose output", "prevent destructive actions" → skill |
| **Directory CLAUDE.md** vs **rules + `paths:`** | The convention belongs to *one stable folder* | The convention belongs to a *file type* spread across folders | "all `*.test.tsx`", "wherever" → `paths:` |
| **`@import`** vs **rules + `paths:`** | Each package's CLAUDE.md pulls in just the standards files it needs; imported content is always loaded | Parts should load only when matching files are edited | "each package needs different standards" → `@import`; "only when editing…" → `paths:` |
| **CLAUDE.md** vs **hook** | Guidance that usually applies | A guarantee with no exceptions | "must never", "every time" → hook |
| **Project** vs **user** scope | Team standard, new hires need it | Personal preference or experiment | "the team" / "just me" |
| **Plan mode** vs **direct execution** | Large, multi-file, several possible designs | Clear, small, well-scoped change | "45 files", "two possible approaches" → plan |

Remember that "put the command in CLAUDE.md" is not a way to create a `/command`. CLAUDE.md holds context. A command is its own file in `.claude/commands/`.

## Tools and API pairs

| Pair | First | Second | Deciding word |
|---|---|---|---|
| **Grep** vs **Glob** | Searches file **contents**: function names, error strings, imports | Matches file **paths**: `**/*.test.tsx` | "files named…" → Glob; "where is X called" → Grep |
| **Edit** vs **Read + Write** | Targeted change, anchor text is unique | Edit failed because the anchor is not unique: read the whole file, then write it back | "appears several times" → Read + Write |
| `"any"` vs **forced** `tool_choice` | Must call a tool, any tool is fine | Must call *this* tool first | "before enrichment", "first step" → forced |
| **`PreToolUse`** vs **`PostToolUse`** | Stop or redirect a call *before* it runs | Change a result *after* it ran, before Claude sees it | "block", "limit" → Pre; "normalise", "trim fields" → Post |
| **MCP tool** vs **MCP resource** | An action or query with inputs | A catalog to *look at*: docs tree, schema, issue list | "agent keeps guessing what exists" → resource |
| **Error** vs **empty result** | Could not run: `isError: true` + category | Ran, found nothing: `isError: false`, empty | "timeout" vs "no matches" |
| **Rename** vs **split** a tool | Two tools overlap in purpose (`analyze_content` → `extract_web_results`) | One tool does too many things (`analyze_document` → `extract_data_points`, `summarize_content`, `verify_claim_against_source`) | "confused with another tool" vs "does everything" |

Tracing a function that is re-exported under another name? **Grep twice**: first for the exported aliases, then for each alias. Searching only the original name misses callers.

## Context and session pairs

| Pair | First | Second | Deciding word |
|---|---|---|---|
| **Resume** vs **fork** | Continue *one* line of work | Try *two* directions from the same baseline | "compare two approaches" → fork |
| **Resume** vs **fresh + summary** | Earlier tool results are still valid (name any changed files) | Earlier tool results are largely stale | "files changed a lot", "weeks later" → fresh |
| **`/compact`** vs **Explore subagent** | Context is *already* full; keep going in this session | Keep verbose discovery *out* of the main context to begin with | "about to explore" → Explore; "already full" → `/compact` |
| **Progressive summarisation** vs **case-facts block** | Old conversation turns can be condensed | Numbers, IDs, dates and customer requests must stay exact | "$89.99 became 'about $90'" → case facts |
| **Scratchpad** vs **`/compact`** | Findings must survive a reset or a new session | Just reduce context now | "later session", "context reset" → scratchpad |
| **Coordinator** vs **subagent** handles an error | The subagent couldn't recover locally | Transient failure the subagent can retry itself | "timeout" → subagent first, then report up |

Placement also matters: put **key findings first** and use clear section headers. Content in the middle of a long input is the most likely to be missed.

## Output, review and batch pairs

| Pair | First | Second | Deciding word |
|---|---|---|---|
| **Nullable** vs **`"unclear"`** vs **`"other"`** | Value absent from the source → `null` | Present but ambiguous → `"unclear"` | Present, clear, but not in the list → `"other"` + detail |
| **Retry with feedback** vs **accept null** | Format or structure error | Information isn't in the provided document | "the contract doesn't state…" → null |
| **Retry** vs **`conflict_detected`** | The model extracted the wrong value | The source contradicts itself (stated total ≠ sum of items) | "the invoice itself says…" → flag the conflict |
| **Synchronous** vs **Batches** | Someone waits; pre-merge check | Latency-tolerant: overnight reports, weekly audits, nightly test generation | "blocking" vs "by tomorrow morning" |
| **Resubmit by `custom_id`** vs **sample first** | A few items failed (e.g. too long) | A new document type, prompt not tested yet | "about to submit 10,000 new…" → sample first |
| **Per-file pass** vs **integration pass** | Local bugs inside one file | Issues *between* files: types, contracts, cycles | Large PR → do both |
| **Self-review** vs **independent instance** | Not a real review: it keeps the reasoning that made the choices | Reviewing generated code, e.g. in CI | "same session" → independent |
| **Explicit criteria** vs **"be conservative"** | Report X, skip Y, with examples | Never: it is not checkable | "false positives" → explicit criteria |
| **Few-shot** vs **longer prose** | Output varies on ambiguous inputs; extraction returns empty/null or invented values on varied document formats | Rarely: detail alone doesn't generalise | "inconsistent format", "different document layouts" → 2–4 examples |

> **Key idea:** when two options both look right, ask which one matches the *specific* symptom in the stem. The other one usually solves a neighbouring problem.

## Exam-guide details that are easy to miss

Small "Skills in" bullets from the exam guide that decide questions but are easy to forget. Read them as *situation → move*.

**Iterative refinement (3.5)**
- Prose description gives inconsistent results → give **2–3 concrete input/output examples**.
- New feature → write the **test suite first** (behaviour, edge cases, performance), then iterate by sharing the **specific failing tests**, not by re-explaining the requirement.
- Unfamiliar domain (e.g. caching) → **interview pattern**: let Claude ask about invalidation strategy, failure modes, etc. before it implements.
- Several issues: fixes **interact** → one detailed message. Issues are **independent** → fix them one at a time.
- One edge case keeps failing (e.g. nulls in a migration script) → give that specific input and its expected output.

**Coordinator design (1.2, 1.3)**
- Pick the subagents a query actually needs; don't always run the full pipeline.
- Split scope so subagents don't duplicate each other (distinct subtopics or source types).
- Coordinator prompts state **goals and quality criteria**, not step-by-step procedures, so subagents can adapt.
- Coverage gap after synthesis → re-delegate a **targeted** query, then re-run synthesis.

**Decomposition (1.4, 1.6)**
- One customer message with three problems → split into items, investigate them in parallel with shared context, answer with **one** combined resolution.
- "Add tests to this legacy codebase" → map the structure, find high-impact areas, make a prioritised plan that **adapts** as you learn. Fixed pipelines suit predictable reviews.

**Tools (2.3, 2.4, 2.5)**
- Synthesis agent needs quick fact checks often → give it a narrow `verify_fact` tool for the simple, frequent cases; complex verification still goes through the coordinator.
- Generic `fetch_url` → constrained `load_document` that validates the URL.
- MCP tools are discovered when the server connects.
- New codebase → Grep for entry points, then Read along the imports. Don't read everything first.

**Escalation and context (5.1, 5.2)**
- Customer asks for a human → escalate **immediately**, no investigation first.
- Customer is frustrated but the issue is solvable → acknowledge it, offer the fix, escalate only if they **ask again**.
- Policy is silent (competitor price match when policy covers only own-site prices) → escalate.
- Downstream agent has a small context budget → upstream agents return **structured facts, citations and relevance scores**, not long reasoning.
