# CLI, commands, real-vs-fake and hard numbers

## CLI flags that actually exist

The exam guide lists only a handful of CLI flags. Know what each one **prevents**:

| Flag | Does | Without it |
|---|---|---|
| `-p` / `--print` | Runs the prompt, prints to stdout, exits. Non-interactive | The CI job **hangs**, waiting for input |
| `--output-format json` | Output is JSON instead of prose | Your script has to parse free text |
| `--json-schema '<schema>'` | Output must match your schema | JSON may be valid but have the wrong shape for your PR-comment poster |
| `--resume <session-name>` | Continues a named session | You rebuild context by hand |

The CI command you should be able to write from memory:

```bash
claude -p "Review this PR for security issues" \
  --output-format json \
  --json-schema '{"type":"object", ...}'
```

CI habits that come with it:
- The review runs in a **separate** instance, not in the session that wrote the code.
- Put the **earlier review findings** into context and ask only for new or still-open issues. Otherwise every re-run repeats fixed issues.
- Put the **existing test files** into context when generating tests, so you don't get duplicates.
- The CI agent reads the project CLAUDE.md like any session. Put testing standards and review criteria there.

## Real or fake?

Distractors use names that sound right. All of these are **invented or ineffective**:

| Distractor | What people wanted | The real thing |
|---|---|---|
| `CLAUDE_HEADLESS=true` | Stop the CI hang | `-p` / `--print` |
| `--batch` flag | Non-interactive / bulk run | `-p` (and the Message Batches **API** is a separate product) |
| stdin from `/dev/null` (a real Unix trick, not a Claude Code feature) | Stop the hang | `-p` |
| `.claude/config.json` with a `"commands"` array | Define slash commands | One file per command in `.claude/commands/` |
| `.claude/config.yaml` mapping file patterns to CLAUDE.md sections | Conditional rules | `.claude/rules/*.md` + `paths:` |
| `--strict` next to `--json-schema` | "Turn on" the schema | `--json-schema` works alone (use with `--output-format json`) |
| `--refresh` on resume | Reload changed files | Tell the resumed session which files changed |
| `override: true` in SKILL.md | Personal skill wins over team skill | A personal skill with a **different name** |
| `import(path)` in CLAUDE.md | Modular CLAUDE.md | `@path` |
| `session_id` API parameter | Server remembers the chat | Send the full `messages` history each call |
| `"role": "tool"` message | Return a tool result | `tool_result` block inside a `user` message |

Other invented *behaviours* the question bank uses: CLAUDE.md "expires" after an hour, rule files have priorities, a frontmatter typo is auto-corrected, Edit falls back to the first match, Write can't change booleans.

> **Note (current docs):** a few near-misses exist today: a bundled `/batch` **skill** (splits large changes into parallel tasks) and `--strict` on `claude plugin validate`. Neither is a `--batch` CLI flag or a switch for `--json-schema`.

> **Key idea:** the exam guide's list of technologies is short and closed. A plausible-sounding flag or key that isn't on it is almost always the wrong option.

## In-session commands and context tools

| Tool | Use when | Not for |
|---|---|---|
| `/memory` | An instruction seems ignored: check which memory files actually loaded | Syncing rules to teammates |
| `/compact` | A long exploration filled context with file reads and grep output; you want to keep going in the same session | Keeping exact numbers safe. Summaries lose detail, so put key facts in a case-facts block or scratchpad |
| Plan mode | Big or unclear change: dozens of files, several possible architectures. It only reads until the plan is approved | A one-file fix with a clear stack trace (just do it) |
| Explore subagent | Verbose discovery (read 15 files, trace imports) that should come back as a short summary | Tasks that need the full detail in the main context |
| Scratchpad file | Record key findings (paths, classes, constraints) that must survive context loss or a new session | Replacing the actual code reading |
| State manifest (e.g. `agent-state/manifest.json`) | A multi-agent run crashed; on resume, reload each agent's saved state instead of restarting everything | Single-session work |

Common pairing: explore in plan mode (or with Explore), write findings to a scratchpad, then execute directly.

## The numbers sheet

| Number | Where it shows up |
|---|---|
| **60 / 120 / 720** | Questions / minutes / passing score (scale 100–1000) |
| **4 of 6** | Scenarios drawn per exam from the bank of six |
| **27 · 18 · 20 · 20 · 15 %** | Domains 1–5 weights |
| **50 %** | Message Batches discount |
| **24 h** | Maximum batch processing time. No latency SLA |
| **30 h SLA → 4 h windows** | Batch submission frequency (exam guide example). Collect for one window, then submit: window wait + up to 24 h processing must stay inside the SLA, with margin (4 + 24 = 28 ≤ 30) |
| **4–5 tools** | Per agent, selects reliably. **18 tools** degrades selection |
| **2–4 examples** | Few-shot for ambiguous cases (2–3 input/output pairs to pin down a transformation) |
| **$500** | Refund limit enforced by a `PreToolUse` hook |
| **40+ fields → ~5** | Order lookup trimmed by a `PostToolUse` hook |
| **97 %** | Headline accuracy that can hide one bad document type. Break it down |
| **45+ files** | Migration size that calls for plan mode |

> **Exam trap:** numbers are often in the stem just to tempt you into arithmetic or a round threshold. "Confidence ≥ 0.9 sounds strict" is not calibration. A threshold means something only after you check it against a labeled validation set.
