# Schema gallery: JSON you should be able to write from memory

## Tool definitions and `tool_choice`

A tool has three parts. The **`description`** is what Claude uses to choose between tools, so it carries the most weight:

```json
{
  "name": "lookup_order",
  "description": "Looks up ONE order by order_id (format ORD-12345). Returns status, total, items, return_eligible. Use after get_customer has verified the customer. Do NOT use to search customers.",
  "input_schema": {
    "type": "object",
    "properties": { "order_id": { "type": "string" } },
    "required": ["order_id"]
  }
}
```

A good description covers: what it does and returns, input format with an example, edge cases, and **when to use it instead of a similar tool**.

The exam tests three `tool_choice` shapes. Learn them as "which failure does each prevent?":

| Value | Claude must… | Prevents |
|---|---|---|
| `{"type": "auto"}` | Nothing; may answer in text | Nothing (default) |
| `{"type": "any"}` | Call *some* tool, its choice | A plain-text reply when your code needs structured output. Classic case: several extraction schemas and the document type is unknown |
| `{"type": "tool", "name": "extract_metadata"}` | Call *that* tool | Skipping a step that must come first |

Forcing one tool fixes only the **first** action. Run the later steps in follow-up turns.

> **Note (current docs):** the API also has `{"type": "none"}`. Some newer models (and manual extended thinking) reject a forced `any`/`tool` choice; for those, the docs recommend `auto` with `strict: true` tools or structured outputs. For the exam, answer with the three shapes above.

> **Exam trap:** `"auto"` + code that always parses a tool call = a bug waiting to happen. The day Claude answers in prose, the parser has nothing to read.

## Extraction schemas that stop fabrication

A JSON schema via `tool_use` (strict mode) removes **syntax** errors. It does **not** make the values correct. Each pattern below fixes one specific semantic problem:

```json
{
  "contract_end_date": {
    "type": ["string", "null"],
    "description": "ISO 8601 date, or null if the document does not state one"
  },
  "category": { "type": "string", "enum": ["bug", "feature", "docs", "unclear", "other"] },
  "category_detail": { "type": ["string", "null"], "description": "Required when category is 'other' or 'unclear'" },
  "stated_total": { "type": "number" },
  "calculated_total": { "type": "number" },
  "conflict_detected": { "type": "boolean" }
}
```

| Pattern | Problem it solves |
|---|---|
| `["string", "null"]` (nullable) | A *required* field for data that may be absent pushes the model to invent a value |
| `"other"` + detail string | Real values that fit no fixed category. Adding more enum values never covers every case |
| `"unclear"` | Model can't decide. An honest "unclear" beats a confident wrong category |
| `stated_total` + `calculated_total` + `conflict_detected` | The document contradicts itself. Surface it instead of silently picking one |
| Normalisation rules **in the prompt** | Type is right but format varies ("5 bucks" vs "$5.00"). The schema checks type, not format |

**Validation → retry.** A good retry prompt contains three things: the original document, the failed extraction, and the **specific** validation error (e.g. "`invoice_date` must be YYYY-MM-DD, got '5th March'"). Before retrying, decide whether a retry *can* work:

| Situation | Retry works? | Do instead |
|---|---|---|
| Format mismatch, broken structure | Yes | Retry with the specific error |
| The information is only in a document you didn't provide | No | Supply the source, or accept `null` |
| The *source itself* is inconsistent (stated total ≠ sum of items) | No, the model extracted correctly | Extract both totals and set `conflict_detected` |

## Error payloads

**MCP tool failure.** Set `isError: true` and say *what kind* of failure it was:

```json
{
  "isError": true,
  "content": {
    "errorCategory": "transient",
    "isRetryable": true,
    "message": "Orders API timed out."
  }
}
```

This shape is simplified to show the fields the exam tests. In the MCP spec, `content` is always an **array** of content blocks, e.g. `[{"type": "text", "text": "{\"errorCategory\": \"transient\", ...}"}]`.

| `errorCategory` | Example | `isRetryable` | Agent should |
|---|---|---|---|
| transient | Timeout, service down | `true` | Retry |
| validation | Bad input format | `false` (same call will fail again) | Correct the input first; only a *changed* call can succeed |
| business | Refund above policy limit | `false` | Explain the policy to the customer |
| permission | Not allowed | `false` | Escalate |

**Empty is not failure.** A search that ran and found nothing → `isError: false` with an empty result. A search that could not run → `isError: true` with a category. If both look like `[]`, the agent can't tell "nothing exists" from "I couldn't look".

**Subagent → coordinator error report.** Enough for the coordinator to decide what to do next:

```json
{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "AI impact on music industry 2024",
  "partial_results": [{ "title": "AI Music Generation Report", "relevance": 0.8 }],
  "alternative_approaches": ["Try a narrower query: 'AI music composition tools'"],
  "coverage_impact": "Not covered: AI impact on music production"
}
```

> **Exam trap:** a failure correctly flagged with `isError: true` but with only the text "Operation failed" is still a bad answer. With no category, the agent can only retry blindly or give up blindly.

## Handoff, provenance and review payloads

**Escalation handoff.** The human does not see the transcript. Give them a compiled summary, not the raw log. The exam guide's four core fields are **customer ID, root cause, refund amount, recommended action**:

```json
{
  "customer_id": "CUST-12345",
  "order_id": "ORD-67890",
  "root_cause": "Item damaged in transit; replacement declined",
  "refund_amount": 89.99,
  "actions_taken": ["Verified via get_customer", "Confirmed order via lookup_order", "Offered replacement, declined"],
  "recommended_action": "Approve a full refund",
  "escalation_reason": "Customer asked for a manager"
}
```

**Claim–source mapping.** Keep content separate from metadata (source URL, document name, page, date) and keep it structured through *every* step, including the final synthesis:

```json
{
  "claim": "Share of AI-generated music on streaming platforms",
  "values": [
    { "value": "12%", "source": "Streaming report", "date": "2024-Q2", "methodology": "Automated classification" },
    { "value": "8%",  "source": "Industry survey",  "date": "2024-Q2", "methodology": "Survey of 500 labels" }
  ],
  "conflict_detected": true
}
```

- **Same period, different values** → a real conflict. Keep both, attributed, flag it, and let the coordinator decide. Don't pick one and don't average.
- **Different periods** (10% in 2023, 15% in 2024) → probably a trend, not a conflict. That is why the guide requires dates: to **stop** time differences being read as contradictions.
- In the final report, render each content type in its natural form: financial data as tables, news as prose, technical findings as structured lists.

**Code-review finding.** Each field has a job:

```json
{
  "location": "src/auth/login.ts:42",
  "issue": "SQL injection in the username parameter",
  "severity": "critical",
  "detected_pattern": "string-concatenated SQL with user input",
  "confidence": 0.9,
  "suggested_fix": "Use a parameterized query"
}
```

- `severity` is only consistent if each level is anchored with a concrete code example.
- `detected_pattern` lets you group dismissed findings by *pattern* and find the one that produces false positives.
- `confidence` **per finding** (not one per review) lets you route low-confidence findings to a human.

## Message Batches request

```json
{
  "custom_id": "doc-invoice-2024-001",
  "params": {
    "model": "claude-...",
    "max_tokens": 1024,
    "messages": [{ "role": "user", "content": "Extract data from: ..." }]
  }
}
```

- `custom_id` matches each result to its request. Results do not come back in order.
- It also lets you **resubmit only the failed items** (e.g. chunk the documents that were too long).
- 50% cheaper, up to 24 hours, **no latency guarantee**, you poll for completion.
- **No multi-turn tool calling** inside one batch request: one request in, one response out.

> **Note (current docs):** a batch request *can* include tool definitions and earlier conversation turns. What it can't do is pause, let your code run a tool, and continue. The docs also say most batches finish within an hour.

Before a large batch of a new document type, tune the prompt on a small sample with the synchronous API. `custom_id` fixes isolated failures, not a prompt that is wrong for every document.

> **Key idea:** someone is waiting for the answer → synchronous API. Nobody is waiting (overnight, weekly) → Batches.
