# Trick-question families and how to spot them

## Read the stem for the deciding word

Almost every question has four options that would "work". The stem usually contains one word or number that decides which one wins. Find it **before** you read the options.

| The stem says… | It is testing… | Usually wins |
|---|---|---|
| "always", "never", "must", "guarantee", money, identity, compliance | Deterministic vs probabilistic | Hook, prerequisite gate, forced `tool_choice`, schema, deny rule |
| "most effective **first** step", "lowest effort" | Proportion | The small fix at the root cause, not new infrastructure |
| "**root cause**", "every subagent did its job, yet…" | Which layer is at fault | Something upstream (decomposition, description, scope), not the last step |
| "user is waiting", "blocks the merge" | Latency | Synchronous API |
| "overnight", "weekly audit", "nightly test generation" | Latency tolerance: nobody is waiting | Message Batches (volume alone doesn't decide it) |
| "the whole team", "new hires", "every developer" | Scope | Project-level, committed file |
| "only me", "experimenting" | Scope | `~/` user-level file |
| "all test files", "wherever they are" | Pattern scope | `.claude/rules/` + `paths:` glob |
| "reviews its own…", "same session" | Independence | A separate instance |
| A percentage or a confidence score | Proxy vs real signal | Break it down / calibrate it |

Then check each option against **one** question: *does this actually guarantee it, and is it the right size for the problem?* The next four chunks group the distractors into families. Once you know the family, the wrong options are easier to spot.

## Family A: asking nicely where code is needed

**The tell:** the requirement is absolute ("must never", "every time", refunds, identity checks), and the option only changes what Claude *reads*.

| Requirement | Distractor (probabilistic) | Winner (deterministic) |
|---|---|---|
| Verify identity before any refund | Stronger system prompt; few-shot examples of verifying first | Gate that blocks `process_refund` until `get_customer` returned a verified ID |
| Never refund over $500 | "NEVER exceed $500" in CLAUDE.md | `PreToolUse` hook that blocks and escalates |
| Extraction must always return structured data | "Always respond with JSON" | `tool_use` + schema; `tool_choice: "any"` or forced |
| Metadata extraction must run first | "Please start with metadata" | `tool_choice: {"type": "tool", "name": "extract_metadata"}` |
| JSON sometimes won't parse | "Double-check your JSON" | Schema via `tool_use` |

**Family A's twin — self-review.** The tell: "the same session / same instance checks its work". Self-review instructions, extended thinking, or "double-check before finishing" all still run **inside the context that made the decision**. That context already justifies the choice. The fix is an **independent instance** with no generation reasoning.

> **Key idea:** if the stem says the rule must hold 100% of the time, every prompt-only option loses. That includes CLAUDE.md, rules files and skills.

## Family B: "more" and unreliable proxies

**"More" fixes.** The tell: the option makes something **bigger** instead of **better organised**.

| "More" distractor | Why it fails | Winner |
|---|---|---|
| Bigger context window | Attention dilution and lost-in-the-middle are about *attention*, not capacity | Per-file passes + integration pass; key findings first; section headers |
| More tools "for flexibility" | 18 tools make selection worse | 4–5 tools scoped to the role |
| 10 more few-shot examples | Near-duplicates add cost, not judgement | 2–4 varied examples with a short *why* |
| More review categories | Adds noise when one category already has too many false positives | Fix or temporarily disable the noisy category |
| More retries | Can't create data that isn't in the source | Accept `null` after a limited budget |
| Bigger random sample | A 2% document type barely shows up | Stratified sample per segment |

**Unreliable proxies.** The tell: a signal that is *easy to measure* stands in for the thing you actually care about.

| Proxy | Why it misleads | Real signal |
|---|---|---|
| Customer sentiment → escalate | Anger doesn't mean the case is complex | Explicit request for a human, policy gap, no progress |
| Model's self-reported confidence | Poorly calibrated; confidently wrong on hard cases | Confidence calibrated on a labeled validation set |
| 97% overall accuracy | Averages hide a weak segment | Accuracy per document type and field |
| Response has text / says "done" | Not a contract | `stop_reason == "end_turn"` |
| "Most recent order" when several customers match | A guess | Ask for another identifier |
| "Be conservative", "only high confidence" | No checkable rule | Explicit criteria: report X, skip Y |

## Family C: right fix, wrong layer

**The tell:** the stem shows every downstream part working correctly, and the option fixes a downstream part.

| Symptom | Distractor blames… | Actual layer |
|---|---|---|
| Research report covers only part of the topic, yet each subagent did its task well | Synthesis agent ("detect gaps") or search queries | Coordinator's **task decomposition** |
| Agent mixes up two tools | Few-shot routing examples; a routing classifier | The two tool **descriptions** overlap |
| Agent uses Grep instead of the better MCP tool | Remove Grep | The MCP tool's **description** is too thin |
| Subagent "should have known" what a sibling found | Shared state between subagents | The coordinator didn't put it in the **`Task` prompt** |
| Instruction ignored | Rewrite with capital letters | Check with `/memory` whether the file even **loaded** |
| Keyword in the system prompt ("verify") pulls the wrong tool | Tool implementation | The **system prompt wording** creates the association |

**Family C's twin — over-engineering.** The tell: new infrastructure where a first-step fix exists.

| Over-engineered | Proportionate |
|---|---|
| ML classifier / routing layer | Better descriptions or explicit criteria |
| Custom MCP server for GitHub | Community server |
| Batch API with synchronous fallback for a blocking check | Just use synchronous |
| Restart the whole research pipeline on a gap | Re-delegate one targeted query, then re-synthesise |
| Redo the whole investigation for each approach | `fork_session` from the shared baseline |
| Re-explore the whole codebase after a resume | Name the changed files |

## Family D: hiding information vs overreacting

**The tell:** something went wrong, and the option either **hides** it or **stops everything** because of it. The winner sits in the middle: pass the problem on, with structure, to whoever can decide.

| Hides it | Overreacts | Winner |
|---|---|---|
| Empty result marked as success | Stop the whole multi-agent workflow | Structured error: type, query, partial results, alternatives. Try to recover locally first |
| Generic "Operation failed" | Always escalate every error | `errorCategory` + `isRetryable` + a readable message |
| Pick the "more credible" source, or average the two | Drop the claim entirely | Keep both values, attributed, `conflict_detected: true` |
| Report with no gaps shown | Refuse to publish | Mark sections as partial coverage and say why |
| Handoff = raw transcript | Escalate without any context | Structured summary: IDs, root cause, actions taken, recommendation |
| Add a disclaimer to a noisy review category | Delete the category for good | Disable it temporarily, tighten its criteria, re-enable |

**Wrong scope** is the last common family. The tell: the fix is right, but it lives in the wrong place.
- Team rule in `~/.claude/CLAUDE.md` → it's in the wrong scope; needs the project file.
- Experimental MCP server in `.mcp.json` → it's in the wrong scope; belongs in `~/.claude.json`.
- One CLAUDE.md per folder for a *file-type* rule → should be a single rules file with `paths:`.
- Personal skill with the **same** name as the team skill → give it a different name.

> **Exam trap:** the "hides it" options often look the *calmest* and the most user-friendly. The exam treats hidden failures as worse than visible ones, because nobody downstream can recover from what they can't see.
